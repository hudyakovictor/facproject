## 1. Главная находка: режим INSPECTOR был имитацией

`AnalysisViews.tsx` выводил список галочек:

```
✓ Mesh 35 709 vertices   ✓ Landmarks 106/134   ✓ Observed UV only
✓ Heatmap z-score        ✓ Morph A→B
```

Фактически рядом рисовались 17 концентрических эллипсов и 21 кривая Безье,
а `MeshViewer` в этом файле **даже не импортировался**. То есть интерфейс
утверждал наличие пяти возможностей, не реализовав ни одной, — при том что
рабочий `MeshViewer` с подлинной BFM-топологией уже существовал и
использовался в полноэкранном оверлее.

Это прямое нарушение `app6/AGENTS.md` («Запрещено объявлять функцию
verified/complete только потому, что код исполнился без исключения»)
и самый опасный для расследования класс дефекта: журналист видит «3D-модель»
и делает по ней выводы.

**Исправлено:** режим переписан на настоящий `MeshViewer` с реальной
геометрией из `/api/v1/photos/{id}/mesh`, с деградацией до 106/134 landmarks
и честным сообщением, если backend геометрию не отдал.

## 2. Выдуманные метрики, поданные как измерения

| Где | Было | Проблема |

**Исправлено:** производные псевдо-каналы удалены; медиана реализована и
подписана корректно (`t.statMedian`).

## 3. Реальные данные Stage 1, которые интерфейс не показывал

Stage 1 сохраняет рядом с каждым фото (см. `info.json → files`):

* `skin_zone_quality.json` — по 40 зонам: `status`, `exclusion_reasons`,
  `visible_fraction`, `skin_pixels`, `bbox_original`;
* `quality.json → per_zone_quality` — `texture_score_0_1`, `quality_class`,
  `laplacian_var`, `tenengrad_mean`, `highlight_fraction`, `shadow_fraction`,
  `skin_fraction`, `texture_pixels`, `roi_source`;
* `quality.json → global_texture_quality` / `mask_quality`;
* `wrinkle_zones.json` — когда модуль включён.

**Ничего из этого не было доступно ни через API, ни в UI.** На проверочном
кадре это 27 активных и 13 исключённых зон с измеренными значениями.

**Реализовано (без нового анализа кожи):**

* `app6/api/skin_zones.py` — читает артефакты и приводит к одному контракту;
* `GET /api/v1/photos/{id}/skin_zones` — per-zone отчёт;
* `GET /api/v1/zones/catalog` — каталог зон из нормативного атласа;
* `ui/src/components/SkinZonesPanel.tsx` — таблица зон с раскрытием деталей,
  фильтром по анатомической группе, сводкой и перечнем источников;
* панель встроена в `SkinTab` левой панели и в правую колонку INSPECTOR.

Ключевые инварианты:

* отсутствующий канал → `null` и статус `no_data`, показывается как «—»,
  **никогда как 0** (`AGENTS.md`: отсутствующие данные не заменяются нулём);
* в demo-режиме эндпоинт возвращает **HTTP 409 с объяснением**, а не
  синтетические числа — панель показывает причину;
* веса зон не выдуманы: атлас их не содержит, а изобретать их в API значило бы
  подменить нормативную схему.

## 5. Экспорт: был непарсируемым

ТЗ: «экспорт результатов ... JSON для интеграции с другими системами».
Существовал только `window.open` + `document.write` HTML-текста — такой вывод
нельзя ни распарсить, ни приложить к отчёту как данные.

**Добавлен** `ui/src/export.ts` + кнопка «ЭКСПОРТ JSON»: схема
`deeputin.analysis-export.v1`, медианные агрегаты, распределения по позам /
эпохам / гипотезам / evidence-состояниям, список аномалий, полный слепок
фильтров (иначе цифры невоспроизводимы) и обязательные `source_mode` +
`not_a_verdict`, чтобы demo-срез нельзя было принять за результат
исследования.

## 6. Что осознанно НЕ реализовано и почему

| Пункт ТЗ | Причина |
|---|---|
| FFT-спектр, карта альбедо, карта LBP, поры/блеск как **изображения** | Требуют нового пиксельного анализа — исключено требованием заказчика. Числовые характеристики качества текстуры выведены из уже сохранённых артефактов |
| PDF-отчёт с визуализациями | Требует тяжёлой зависимости рендеринга; JSON-экспорт (машиночитаемый) реализован как более приоритетный по ТЗ |
| Перетаскивание миниатюр по временной оси | Дата — неизменяемый факт из имени файла (`AGENTS.md`); перетаскивание означало бы правку датировки мышью |
| Многопользовательский режим, роли, аудит действий | В самом ТЗ помечено «если это применимо»; для локального инструмента одного журналиста создаёт ложное ощущение контроля доступа |
| Undo/redo, заметки и теги, clipboard | Не затрагивают достоверность анализа; вынесены за рамки как UX-надстройка |
| `POST /api/v1/compare/upload` | Backend честно отвечает 501 без Stage 1; кнопка в UI создала бы тупик |
| `detail_level` (simple/standard/expert) | Сохраняется на backend, но пока ни на что не влияет — **остаётся долгом**, отмечен ниже |

## 8. Оставшийся долг

1. **`detail_level` ни на что не влияет** — уровень детализации сохраняется,
   но интерфейс не меняет плотность информации. Нужно связать с показом
   диагностических полей (`roi_source`, `laplacian_var`, `tenengrad_mean`).
2. **Кривая ожидаемого старения** на таймлайне (ТЗ: «линиями показывающими
   ожидаемое старение») — требует модели старения из Stage 2; сейчас в
   `/api/v1/timeline` такого канала нет.
3. **Связи между точками таймлайна** для результатов попарного сравнения.
4. **Уведомления о критических событиях** — есть баннеры ошибок в отдельных
   разделах, но нет единого центра уведомлений.
