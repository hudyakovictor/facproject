# Карта размещения ключей пайплайна в интерфейсе

**Дата:** 2026-07-29
**Основание:** `ui/PIPELINE_KEYS_GAP.md` (топ-50 ключей без реализации).
**Задача этого документа:** 30 дополнительных анализов, цель которых — найти
не «какие ключи потеряны» (это уже известно), а **куда именно в существующем
интерфейсе их можно поставить**, и свести результат в приоритетные категории,
покрывающие *весь* набор невидимых ключей, а не топ-N.

### 🔴 A — Статистическая достоверность и корроборация · 12 пунктов / 28 ключей

Единственная категория, где отсутствие ключа даёт не неполноту, а
**неверный вывод**: интерфейс показывает расхождение как аномалию, хотя
пайплайн уже посчитал, что оно не переживает поправку на множественные
сравнения или не подтверждается в других ракурсах.

| # | Ключи | Куда | Как |
|---|---|---|---|
| A1 | `mt_p_approx`, `mt_q_value`, `mt_significant_fdr10`, `mt_fdr10_diagnostic_flag`, `mt_role` (5) | `PairCompareView` → правая колонка, **новая карточка «Статзначимость»** выше `MetricsTable` | q-value крупно, значок «проходит/не проходит FDR-10», роль пары в семье гипотез |
| A2 | `primary_robust_z`, `primary_calibration_p95` (2) | Шапка той же карточки | Пара «z / порог» рядом с сырым расхождением |
| A3 | `matched_calibration_sets` (1) | Подпись карточки A1 | «Калибровано по N наборам» — без этого z-оценка бессмысленна |
| A4 | `cross_bin_corroboration_status`, `cross_bin_support_count`, `cross_bin_support_pose_count`, `cross_bin_support_pose_bins`, `cross_bin_independent_source_count`, `cross_bin_family_matched_count` (6) | `PairCompareView` → **карточка «Корроборация»** сразу под A1 | Список ракурсов, подтверждающих расхождение + число независимых источников |
| A5 | `calibration_limited`, `calibration_limitation_reason` (2) | Шапка `PairCompareView`, рядом со `status` | Бейдж-предупреждение, а не строка в таблице |
| A6 | `pose_leakage_limited` (1) | Туда же | Бейдж «метрика коррелирует с позой» |
| A7 | `pose_leakage_status`, `pose_leakage_flagged_metrics`, `pose_leakage_limited_pair_count` (3) | Раздел «Калибровка» → **карточка «Утечка позы»** | Прогон-уровень: список помеченных метрик |
| A8 | `calibration_limited_pair_count`, `multiple_testing_pair_count` (2) | Режим `STATS` → полоса «Охват статистики» | Сколько пар вообще получили поправку |
| A9 | `multiple_testing.json` (1) | `STATS` → раскрывающаяся таблица q-value по всем парам | Сортировка по q, а не по сырой величине |
| A10 | `cross_bin_corroboration.json` (1) | Туда же, вторая вкладка | Матрица «пара × pose bin» |
| A11 | `pose_leakage_diagnostic.json`, `calibration_sensitivity.json` (2) | Раздел «Калибровка», рядом с A7 | Устойчивость: не держится ли вывод на одной персоне |
| A12 | `analysis_validation.json`, `evidence_packets.json` (2) | Режим `DATA` → «Целостность прогона» | Валидация схемы + число сформированных пакетов доказательств |

**Зависимость:** A1–A6 требуют нового эндпоинта пары (анализ №10).
A7–A12 читаются из уже существующих файлов и могут быть сделаны раньше.

### Категории D–I — состав пунктов

Ключевые списки разворачиваются по запросу; здесь — названия пунктов,

**D — Точки, дескрипторы, выравнивание · 10 пунктов / 29 ключей**

**E — Текстура и структура кожи · 7 пунктов / 17 ключей**

## 3. Порядок выполнения

1. **Эндпоинт пары** `GET /api/v1/pairs/{a}/{b}/metrics`, отдающий строку
   `pair_metrics.csv` целиком. Один эндпоинт разблокирует A, B, C, D, E —
   это ~150 из 289 ключей.
2. **Категория A** — единственная, где текущее состояние даёт риск
   неверного вывода, а не неполноты.
3. **`metric_catalog.json` (I4)** — до массового рендеринга таблиц: снимает
   +26% нагрузки на словарь i18n.
4. **Категория B** — крупнейшая по объёму, минимальная по стоимости на ключ.
5. Далее C → F → G/H → E/D → I.
