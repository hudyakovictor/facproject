# app9/validation — проверка метрик идентичности на калибровке

Один протокол, одна таблица, без пар «до/после починки». Скрипты читают данные и
импортируют `app8`/`morphing`, поэтому запускать из корня репозитория:

```bash
cd /Users/victorkhudyakov/work
PYTHONPATH=/Users/victorkhudyakov/work python app9/validation/advisor_tests.py
```

Кэши (регенерируемые, в git не входят, лежат в `/Users/victorkhudyakov/work/.runtime`):

| кэш | что содержит | как пересоздать |
|---|---|---|
| `level_cache/frames.jsonl` | 606 реконструкций `calibration_rakurs`: углы, R, облака cam/two_d/canon (106 точек), v17. Внимание: в лежащем на диске кэше облака центрированы, но не отмасштабированы (баг `norm()` до правки); `advisor_tests.load()` восстанавливает max-radius при чтении, а свежие выгрузки `level_extract.py` пишут уже нормированные точки | `level_extract.py [bin...]`, ~46 CPU-минут |
| `calib_cache/features.jsonl` | признаки `/Volumes/SDCARD/calibration` (7 персон) | `calib_metrics.py` |
| `rakurs_cache/features.jsonl` | признаки `/Volumes/SDCARD/calibration_rakurs` | `rakurs_noise.py` |

## Что известно на сегодня

Числа пересчитаны после правки `norm()` (облака в кэше наконец отмасштабированы), по
единому критерию ровного кадра (`|tilt|<=2` и `|pitch|<=5`) и по медианам людей
(медиана по людям, а не по всем кадрам сразу: иначе пол диктуют person_01 с 28 кадрами).
Облака и метрики приведены к одной нормировке — max-radius=1 по 106 точкам; кэшированный
`v17` (aligner нормирует по всем 35 709 вершинам) пересчитывается из этих же canon и
живёт рядом как `v17_cache`. Отношение двух нормировок по 17 метрикам: med 1.0252,
p05..p95 1.0000..1.0348, min..max 0.6494..1.5518 — на асимметричных метриках расход
доходит до 1.55, поэтому смешивать их в одном тесте нельзя.

- **Двойной поворот в проде подтверждён числами.** `full_pose_correction_matrix`
  применялась к `vertices_identity_only`, у которого позы уже нет
  (`app8/reconstruction.py`, `app6/stage1/reconstruction.py`). Ratio к шумовому полу на
  фронтале: `canon` 2.15, `canon × R_corr` **4.87**, сырой `cam` 5.08, корректный
  `cam × R_corr` 5.83, `cam × Fz × R_corr` 2.19 (Fz = diag(1,1,−1) из `to_camera`).
  В left_profile: 2.16 / 2.97 / 3.11 / 4.67 / 2.11. То есть продный доворот делал сетку
  почти столь же далёкой от эталона, как неповёрнутый камерный кадр. Патч: доворот только
  к каноническому yaw бина; guard-тесты — `app8/tests/test_geometry.py`.
- **Никакой гарантии у Procrustes-доворота (T1) нет, и это измерено на всех 606 кадрах**:
  `d_best > d_canon` в 79 случаях (13%), доля «не хуже canon» 0.870, медиана выигрыша
  0.0000860 при 5-м перцентиле −0.0000185. Прошняя формулировка «d_best обязан быть не
  больше» была неверной: Procrustes минимизирует сумму квадратов, а `vdist` — среднюю
  длину; на 20 кадрах нулевых нарушений оказалось просто эмпирикой. Отсюда `best` убран
  из `level_verify.py` (там он ещё и считал пол не leave-one-out).
- **Выравнивание «снимает 85% ракурса» — некорректная формулировка.** В identity-сетке
  позы никогда не было (`compute_shape(id, 0)`), поэтому `d_canon/d_cam` по 50 ячейкам
  «человек × бин» даёт медиану 0.158 (размах 0.071–0.697) и измеряет в основном размер
  самого поворота в cam, а не снятый ракурс. Содержательная метрика — ratio к полу
  (медиана по людям: фронтал 2.34, left_light 1.91, right_light 1.49).
- **Честный пол на `calibration_rakurs` построить нельзя**: ровные кадры каждого
  человека — один непрерывный прогон. LOO-пол при этом занижен: по T3 зазор по индексу
  кадра поднимает ratio с 2.15 (gap>0) до 2.90 (gap>5, 2 человека) и 2.21 (gap>15, 1).
  Оценка независимого пола из парных расстояний (деление на √2, потому что расстояние
  между двумя шумными кадрами ≈ √2 больше расстояния кадра до истины) даёт 1.58–2.61.
  Рабочий диапазон `canon` ratio — **1.6–3.0**, а не 1.25–3.0.
- **Нормировка max-radius устойчива.** Прежний вывод «max-radius неустойчив, RMS
  лучше» был артефактом бага: RMS-радиус 62.9–243.4 и «пол» 1.009 у two_d были пикселями.
  После нормировки T4: canon 2.15 (maxr) против 2.09 (rms), cam 5.08 против 5.09 —
  порядок состояний и величины совпадают; разброс канонического масштаба кадра
  0.897–1.015 это реальный дрейф масштаба сети от кадра к кадру.
- **Люди разделяются уверенно.** По T5 (max-radius): min 0.01846 (person_04/person_06),
  медиана 0.03259, пол ровных 0.00142, остаток наклонных 0.00469 — ближайшая пара людей
  в 3.9 раза дальше остатка ракурса и в 13.0 раз выше пола.
- **ICC (T6)** 0.952–0.999 на ровных кадрах, 0.751–0.971 на наклонных. Поправка на
  автокорреляцию прогона (Тьюки, лаги 1–2) снимает не более 0.005, то есть опасение
  «ICC завышен прогоном» количественно мало, но оговорка в отчёте осталась.
- **Детрендинг по yaw (T7) не переносится между людьми**: out-of-sample R² (LOPO — регрессия
  на 5 людях, проверка на 6-м) отрицателен у 5 из 8 метрик (brow_eye_left 10.08 → 10.80 при
  R² = −0.38). Там, где падение большое (brow_span 8.26 → 3.30, 60.1%; eye_anchor_spacing
  3.78 → 1.86, 50.9%), R² вне выборки всё равно ≈0 (−0.07 и −0.05): выигрыш даёт подгонка
  под своих людей, а не закон, переносимый на нового.
- **Минимальная видимая добавка (T8a, `t8_absolute.py`)**: для всех 17 метрик один
  наклонный кадр фронтального эталона даёт порог 0.0012–0.0173, а биас стороны сам
  больше ближайшего реального зазора между людьми — столбец `n_фр` = BIAS везде.
  То есть усреднением кадров того же ракурса разрыв не закрыть; при сравнении внутри
  бина (биас сокращается) зазор закрывается за 10–1853 кадра для 14 метрик из 17.
  VIF(5) = (SE_block/SE_iid)² 0.74–1.42, то есть прежняя формула (t/Δ)² была оптимистична
  умеренно, но именно биас, а не его недооценённый SE, делает цифру «56 кадров для
  ширины носа» несостоятельной (T8b: +2% для person_01 не виден даже на 20 кадрах).
- `report/advisor_tests.json`, `report/t8_absolute.json`, `report/level_verify.json` —
  числа тестов 1–8, абсолютных порогов и парного теста «ровняет ли выравнивание»
  (состояния two_d / cam / canon / sym; `best` и `rotneg` удалены: первый считал пол не
  leave-one-out, второй добавлял позу к сетке без позы — их заменяют колонки T2).
