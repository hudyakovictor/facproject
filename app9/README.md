# app9/validation — проверка метрик идентичности на калибровке

Один протокол, одна таблица, без пар «до/после починки». Скрипты читают данные и
импортируют `app8`/`morphing`, поэтому запускать из корня репозитория:

```bash
cd /Users/victorkhudyakov/work
PYTHONPATH=/Users/victorkhudyakov/work python app9/validation/advisor_tests.py
```

Кэши (регенерируемые, в git не входят, лежат в `/Users/victorkhudyakov/work/.runtime`):

| кэш | что содержит | как пересоздать |
|---|---|---|
| `level_cache/frames.jsonl` | 606 реконструкций `calibration_rakurs`: углы, R, облака cam/two_d/canon (106 точек) и v17. Свежие строки нормированы боевой нормировкой `aligner.normalize_ldm106` и несут сырой масштаб кадра (`cam_rawscale` и т. п.). Строки, выгруженные до правки `norm()`, центрированы, но не отмасштабированы; `advisor_tests.load()` прогоняет их через ту же нормировку — она идемпотентна, поэтому переизвлечение 606 кадров (~46 CPU-минут) не требуется | `level_extract.py [bin...]` |
| `calib_cache_rms106/features.jsonl` | признаки `/Volumes/SDCARD/calibration` (7 персон) в боевой нормировке; прежний `calib_cache` собран в max-radius и не переиспользуется | `calib_metrics.py` |
| `rakurs_cache/features.jsonl` | признаки `/Volumes/SDCARD/calibration_rakurs` | `rakurs_noise.py` |
| `hyp_cache/`, `disc_cache/`, `band_transfer/` | признаки гипотез и перенос между бинами | `hypotheses_check.py`, `robustness_check.py` |

## Что известно на сегодня

Числа пересчитаны после правки `norm()` (облака в кэше наконец отмасштабированы), по
единому критерию ровного кадра (`|tilt|<=2` и `|pitch|<=5`) и по медианам людей
(медиана по людям, а не по всем кадрам сразу: иначе пол диктуют person_01 с 28 кадрами).

**Единицы: одна нормировка с продом.** Облака и метрики юстируются
`morphing.backend.aligner.normalize_ldm106` (центр по 106 ландмаркам, масштаб = RMS по ним
же) — той же функцией, которой прод приводит сетку к канону (патч 04). Расхождение
«прод по 35 709 вершинам против валидации по 106 точкам», из-за которого пороги T6–T8
описывали не тот `v17`, который считает прод, устранено по построению. Абсолютные длины
после перехода выросли примерно в 1.6 раза (`aligner.MAXR_TO_RMS106` = 1.564 для сетки; по
106 точкам фронтальных canon-облаков 1.5645–1.6436, T4), поэтому сравнивать эти цифры с
прогонами до патча 04 напрямую нельзя; безразмерные ratio от перемасштабирования почти не
меняются.

- **Двойной поворот в проде подтверждён — и измеряется без ratio.**
  `full_pose_correction_matrix` применялась к `vertices_identity_only`, у которого позы уже
  нет (`app8/reconstruction.py`, `app6/stage1/reconstruction.py`). На фронтале старый прод
  (`canon × R_corr`) отдалял наклонный кадр того же человека до d = **0.06435**, а ближайшая
  реальная пара разных людей (T5) расходится лишь на **0.02967**: один и тот же человек в
  наклонном кадре становился дальше от самого себя, чем другой человек, в **2.2 раза**.
  Текущий прод (`canon`) даёт 0.00694, то есть 0.23 такого зазора. Те же числа в ratio
  (2.09 против 4.85) годятся только для сравнения состояния с его собственным полом: в
  right_profile ratio у старого прода НИЖЕ (2.40 против 2.66), чем у текущего, хотя d выше
  в 6.3 раза (0.08258 против 0.01316) — поворот домножает пол и d на одно и то же число.
  Поэтому состояния сравниваются колонкой `d/зазор` в T2, а не ratio. Состояния на фронтале
  (d наклонных / ratio / d÷зазор): `canon` 0.00694 / 2.09 / 0.23, `canon × R_corr` 0.06435 /
  4.85 / 2.17, сырой `cam` 0.06332 / 5.09 / 2.13, `cam × R_corr` 0.12698 / 5.82 / 4.28,
  `cam × Fz × R_corr` 0.00778 / 2.08 / 0.26 (Fz = diag(1,1,−1) из `to_camera`). Патч 03 убрал
  доворот совсем (identity-only без поворота бина); guard-тесты — `app8/tests/test_geometry.py`.
- **Никакой гарантии у Procrustes-доворота (T1) нет, и это измерено на всех 606 кадрах**:
  `d_best > d_canon` в 79 случаях (13%), доля «не хуже canon» 0.870, медиана выигрыша
  0.0001544 при 5-м перцентиле −0.0000299. Прошняя формулировка «d_best обязан быть не
  больше» была неверной: Procrustes минимизирует сумму квадратов, а `vdist` — среднюю
  длину; на 20 кадрах нулевых нарушений оказалось просто эмпирикой. Отсюда `best` убран
  из `level_verify.py` (там он ещё и считал пол не leave-one-out).
- **Выравнивание «снимает 85% ракурса» — некорректная формулировка.** В identity-сетке
  позы никогда не было (`compute_shape(id, 0)`), поэтому `d_canon/d_cam` по 50 ячейкам
  «человек × бин» даёт медиану 0.147 (размах 0.071–0.700) и измеряет в основном размер
  самого поворота в cam, а не снятый ракурс. Содержательная метрика — ratio к полу
  (медиана по людям: фронтал 2.34, left_light 1.79, right_light 1.52).
- **Честный пол на `calibration_rakurs` построить нельзя**: ровные кадры каждого
  человека — один непрерывный прогон. LOO-пол при этом занижен: по T3 зазор по индексу
  кадра поднимает ratio с 2.09 (gap>0) до 2.89 (gap>5, 2 человека) и 1.91 (gap>15, 1).
  Оценка независимого пола из парных расстояний (деление на √2, потому что расстояние
  между двумя шумными кадрами ≈ √2 больше расстояния кадра до истины) даёт 1.68–2.70,
  split-half пол — 2.41. Рабочий диапазон `canon` ratio — **1.7–2.7**; прежняя верхняя
  граница 3.0 унаследована от цифры, полученной до правки `norm()`.
- **Масштаб по одной крайней точке неустойчив — поэтому боевая нормировка RMS.** Прежний
  вывод был искажён багом `norm()` и потому перевёрнут: теперь видно и то и другое.
  Сырой масштаб `two_d` = 89.6–390.7 — это пиксели (размер лица на фото), именно он раньше
  выдавался за «неустойчивость max-radius»; после нормировки T4 ratio состояний не
  переворачивается (canon 2.09 RMS против 2.15 max-radius, cam 5.09 против 5.08), но сам
  max-радиус в RMS-единицах скачет по кадрам: 1.5645–1.6436 на фронтальных canon-облаках и
  1.3994–2.0504 по всем состояниям (медиана 1.6209) — порог, заданный долей крайней точки,
  уезжает вместе с ней. Реальный дрейф масштаба сети от кадра к кадру — 0.897–1.015
  (сырой масштаб canon-облака в модельных единицах).
- **Люди разделяются уверенно.** По T5 (RMS-106): min 0.02967 (person_04/person_06),
  медиана 0.04580, max 0.07671; пол ровных 0.00221, остаток наклонных 0.00718 — ближайшая
  пара людей в 4.1 раза дальше остатка ракурса и в 13.4 раза выше пола.
- **ICC (T6)** 0.954–0.999 на ровных кадрах, 0.751–0.994 на наклонных. Поправка на
  автокорреляцию прогона (Тьюки, лаги 1–2) снимает не более 0.005, а при отрицательном ρ₁
  ICC после поправки чуть растёт, то есть опасение «ICC завышен прогоном» количественно
  мало, но оговорка в отчёте осталась.
- **Детрендинг по yaw (T7) плохо переносится между людьми**: out-of-sample R² (LOPO —
  регрессия на 5 людях, проверка на 6-м) отрицателен у 3 из 8 метрик (brow_eye_left
  10.53 → 12.59 при R² = −0.61, brow_eye_right 5.79 → 5.00 при R² = −0.61,
  mouth_nose_offset 7.28 → 9.01 при R² = −0.23). Там, где падение большое (brow_span
  13.58 → 5.34, 60.7%; eye_anchor_spacing 3.77 → 2.26, 40.2%), R² вне выборки всё равно
  ≈0 (0.14 и 0.20): выигрыш даёт подгонка под своих людей. Единственная метрика с
  приличным переносом — nose_ridge_length_3d (5.24 → 4.01, 23.4%, R² = 0.70).
- **Минимальная видимая добавка (T8a, `t8_absolute.py`)**: один наклонный кадр фронтального
  эталона даёт порог 0.0018–0.0271, а биас стороны сам не меньше ближайшего реального зазора
  между людьми — `n_фр` = BIAS для 13 метрик из 17. Для ещё трёх (brow_eye_asym,
  nose_axis_bend_3d, nose_base_asym) зазор_min < 1e-4: ближайшая пара людей совпадает до
  пятого знака, и усреднением такой разрыв не закрывается ни при каком n — метрика различия
  не несёт, и писать про неё «нужно N кадров» некорректно. В бине, где биас сокращается,
  измеренным числом кадров покрыт только один случай (mouth_height_3d, 10 кадров при 16
  наклонных кадров на сторону); остальные 30–1619 помечены `*`, потому что это экстраполяция
  SE ∝ 1/√n за пределы ≤16 реальных кадров, а не измерение; nose_ridge_length_3d уходит за
  `>2000*`. VIF(5) = (SE_block/SE_iid)² 0.89–1.44, то есть прежняя формула (t/Δ)² была
  оптимистична умеренно, но именно биас, а не его недооценённый SE, делает цифру «56 кадров
  для ширины носа» несостоятельной (T8b: +2% для person_01 left не виден даже на 20*
  кадрах).
- `report/advisor_tests.json`, `report/t8_absolute.json`, `report/level_verify.json` —
  числа тестов 1–8, абсолютных порогов и парного теста «ровняет ли выравнивание»
  (состояния two_d / cam / canon / sym; `best` и `rotneg` удалены: первый считал пол не
  leave-one-out, второй добавлял позу к сетке без позы — их заменяют колонки T2).
