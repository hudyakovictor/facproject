# Калибровка v4: чистый таймлайн, landmark-sweep, расширенный корпус

Итерация 4. Геометрия `vertices`, морф-пайплайн и поворотная ветка не тронуты.
Heatmap и график считает один helper `server.heat.compute_heat_values`;
в браузере второй формулы нет. Сырые значения ряда хранятся отдельно от сглаженных.

## Дефолты

| блок | metric | weighting | temporal_filter |
|---|---|---|---|
| heatmap | euclid | none | — |
| chart | euclid | none | none |

Дефолт не менялся: `euclid + none` у heatmap и `euclid + none + none` у графика. Кандидаты включаются только правкой конфига.

Одно изменение отображения без правки конфига: в таймлайне по умолчанию теперь один график (серверный `ChartTrack`); сырые дорожки реестра скрыты и включаются кнопкой «Дорожки».

## Вердикт

**Включить частично: график на baseline, кандидаты — флаги.**

- heatmap — baseline без изменений;
- график — серверный ряд включён на baseline;
- `euclid + calibrated` — флаг конфига (LOTRO 3/4, CI не считался);
- `weighted_normal` — только отчёты (LOPO 5/10, минимум −0.0989);
- `normal` — только отчёты (потеря в челюсти, per-frame не восстанавливает);
- landmark-наборы — ldm68 только для диагностики.

Почему `euclid + calibrated` не включён, хотя гейты графика прошли: тот же профиль
весов проваливает LOTRO на `mid_deep` (ΔAUC −0.0175), CI для него не считался, а сам
профиль между корпусами меняется на 27% по медиане |Δw|. Включать его только в графике
означало бы показывать линию по неутверждённой калибровке. Один флаг в конфиге
(`chart.metric` / `chart.weighting`) включает режим без правок кода.

## B1. Что рисовал Timeline до итерации

`Timeline.tsx` рисовал per-photo значения реестра метрик (`rows[].metrics[id].value`) в сыром пространстве `vertices`/`landmarks_render`: без center+IOD, без normal-компоненты, без калибровки и без временного фильтра. Режимы `value` / `z` / `delta` — три представления одного и того же сырого ряда. `variant="morph"` переиспользует те же дорожки, добавляя ключевые кадры и скраббер.

Теперь ряд считает `server/chart.py` поверх `compute_heat_values` (center + IOD):
`value_raw`, `value_display`, `band`, `significance`; браузер ничего не пересчитывает.

## A. Landmark-sweep

Кадров 210 (7 человек), пар within 454, between 4635.

| набор | within μ | p90 | between μ | ratio | AUC euclid | AUC normal | AUC w-euclid | AUC w-normal |
|---|---|---|---|---|---|---|---|---|
| ldm68 | 0.0548 | 0.0866 | 0.0754 | 1.376 | 0.7649 | 0.7483 | 0.7745 | 0.7671 |
| ldm106 | 0.0537 | 0.0815 | 0.0757 | 1.409 | 0.7766 | 0.7773 | 0.7888 | 0.8035 |
| ldm134 | 0.0442 | 0.0734 | 0.0617 | 1.397 | 0.7604 | 0.7416 | 0.7817 | 0.7754 |

Вывод:
- Лучшее разделение within/between по euclid: ldm106 (AUC 0.7766).
- Взвешивание по landmark-точкам даёт максимальный прирост AUC(euclid) на ldm134 (ΔAUC +0.0208, CI от +0.0099).
- Для normal-компоненты лучший прирост — ldm134 (ΔAUC +0.0339, CI от +0.0218); у ldm68 он +0.0188.
- Профильный контур шумит заметно сильнее внутренних зон: ldm68 ×2.07, ldm106 ×2.11. Для контроля шума в профиле контурные точки стоит держать отдельно от внутренних.
- В ldm134 нет контурных точек профиля (только глаза, брови, рот, нос) — набор не показывает шум контура по построению.
- Рекомендация: для диагностики качества кадра и контроля шума использовать ldm68 — он совпадает с heat space (центр и IOD по его же глазам), покрывает все зоны и даёт ближайший к карте набор точек.
- ldm106 и ldm134 пользователю не выводить: другой набор вершин, сопоставление с ldm68 только по ближайшим точкам, а ldm134 вообще не содержит контура челюсти.

## B6–B7. Интеграция

`GET /api/chart/series?group=…` отдаёт `frames` и `rows` с `value_raw`, `value_display`,
`band`, `significance`, `z_mean`, `z_p95`, `frac_z_gt3`,
`low_confidence_fraction`; семейство перехода (`pose_transition`) считает harness в отчёте, в ответ API оно не входит.
`ChartTrack` рисует полосу, пунктир raw и линию display; `exportPNG` использует те же значения. По умолчанию в таймлайне один график: сырые дорожки реестра скрыты и включаются кнопкой «Дорожки».
Band (`chart_band` профиля): euclid 0.005536, normal 0.002501, weighted_euclid 0.005026, weighted_normal 0.002369.

Паритет API == harness: max|Δ| = 0.0 по 29 шагам на двух людях и четырёх режимах, 0 расхождений полей.
Heatmap preview/export/browser: max|Δ| = 0.0.
Цепочка: join = 0.0 (график), 0.0 (heatmap).

Смена блока `chart` видна без рестарта: тест `config_switch` переключает `temporal_filter` (меняется только `value_display`, `value_raw` побитово тот же) и `metric` (меняются `value_raw` и `band`); возврат конфига возвращает исходную подпись кэша.

## C. Почему normal падает на person_02 и person_05

| человек | euclid | normal | w-euclid | w-normal | jaw euclid | jaw normal | угол нормалей | флипы |
|---|---|---|---|---|---|---|---|---|
| person_02 | 0.783 | 0.694 | 0.837 | 0.747 | 0.648 | 0.517 | 3.28° | 0.0000 |
| person_05 | 0.853 | 0.685 | 0.906 | 0.736 | 0.803 | 0.656 | 3.14° | 0.0000 |

По семействам переходов внутри-пар у этих людей мало: AUC по семейству измерим только для `deep_profile`, остальные три семейства пропущены.

- person_02: within по семействам 0/2/2/10, deep_profile AUC 0.830 → 0.726 (провал воспроизводится);
- person_05: within по семействам 0/2/2/9, deep_profile AUC 1.000 → 1.000 (потолок 1.0, провалу некуда проявиться);

Нормали: средний угол template vs per-frame 3.28°/3.14°, флипов 0.0000/0.0000. Поле нормалей корректно.
AUC по зоне челюсти падает на -0.130 и -0.147; брови, глаза и нос сохраняют разделение. Улыбка/рот как причина не подтверждаются: у person_02 рот даже лучше у normal, у person_05 — тоже.

Per-frame нормали дают ΔAUC -0.002 и 0.013 — провал не возвращается, поэтому в продакшн этот вариант не идёт (в v3 он ещё и рвал стык).

**Итог C:** нормали корректны (угол < 10°, флипов нет), per-frame вариант не возвращает AUC, потеря сосредоточена в челюсти: normal остаётся только в отчётах.
