# ATLAS · узловая лаборатория изменений

**Рабочее приложение:** 3DDFA_V3 на CPU, фото-текстура из реальных пикселей, тепловая карта, морфинг, отдельная панель метрик, α_id-кластеры и измерения глаз на MediaPipe 478-landmark CPU. FAN и AdaFace не подключены. Синтетические demo-карточки можно удалить; рабочий набор по умолчанию не включает demo.

## Открыть

В Arena откройте live preview **«ATLAS — узловая лаборатория»**. Приложение обслуживается на порту 5173. Все запросы из браузера — относительные `/api/...`; отдельный localhost пользователю не нужен.

Восстановление окружения после снапшота (выполняет ИИ-разработчик в среде):

```bash
cd /home/user/atlas
bash scripts/setup.sh
```

Запускать как **долгоживущий процесс**, например через Arena `start_process`:

```bash
cd /home/user/atlas
bash scripts/start.sh
```

Для разработки отдельно: FastAPI на 8000 и Vite на 5173. Production запускается одним `scripts/start.sh` на 5173. После изменений фронтенда `cd web && npm run build` и обновите preview; после Python-изменений перезапустите API. В среде с 2 GB RAM не запускайте сборку одновременно с новым инференсом/UMAP.

## Работа с приложением

### Две рабочие панели

- **«3D · морфинг · фотографии»**: большая сцена с моделью, оригинальной фототекстурой, теплокартой, тремя независимыми наборами landmarks, миниатюрами и общим управлением морфингом.
- **«Таймлайн · измерения»** — отдельная панель дат и метрических дорожек. Курсор связан с 3D-сценой. Ноды можно двигать/менять размер.
- Навигационная полоса: 3D / Метрики / Глаза / Кластеры / Фото и переключатель «рука». Колесо перемещает поле, Ctrl/⌘+колесо масштабирует, Space временно включает перенос; `1–5` переходят к панели, `F` показывает всё поле.

### Окно статуса

- Чип в шапке показывает текущее состояние: «Готово», «В очереди N» или «Работает» («Работает N%» — когда фото в задаче несколько). Клик открывает окно статуса; по умолчанию оно открыто, а сворачивание запоминается. Та же ссылка есть в строке обработки нижнего колонтитула.
- В окне: связь (SSE, ответ `/api/health` и задержка), активные задачи с прогрессом и прошедшим временем, очередь, журнал последних завершённых/отменённых/упавших задач с длительностью, счётчики библиотеки и признаки окружения (FFmpeg, MediaPipe). Это единственное место, где живёт статус обработки: баннер на канвасе появляется только при свёрнутом окне и исчезает сам по завершении, ничего закрывать кнопкой не нужно.
- Обновления приходят по SSE (`/api/events`), поэтому чип и журнал меняются в течение секунды, а не раз в шесть секунд; опрос `/api/health` остаётся запасным путём и служит признаком «сервер жив».
- Если прогресс задачи не меняется дольше 20 секунд, строка получает пометку «нет прогресса N с — задача могла зависнуть», а заголовок окна и чип становятся предупреждающими. Если `/api/health` молчит дольше двух циклов опроса (12 с), состояние меняется на «Сервер не отвечает». Задачу можно отменить прямо из окна.

### Фото и demo

1. В источнике выберите группу или загрузите изображения/ZIP. В ZIP пути папок становятся группами; даты распознаются из имён `2002_12_02`, `2009_12_10_2`, `2003_10_16__hash`.
2. Клик по кадру выбирает реконструкцию; переход между миниатюрами задаёт морфинг пары; Ctrl/⌘ — маршрут из 2–10 кадров. Play/общая перемотка синхронизируют обе панели.
3. Синтетические demo-портреты не выбираются в рабочую группу по умолчанию. Удаление необратимо: стираются запись в библиотеке, копия исходника в `data/groups`, кэш реконструкции и морф-экспорты, где использовалось фото. Файлы на вашем диске, из которых делалась загрузка, не затрагиваются. Повторная загрузка того же файла создаёт запись заново и заново считает реконструкцию.
4. Двойной клик по фото задаёт дату/углы головы; ручные углы не запускают новый inference.
5. Лицо ищет RetinaFace (ResNet-50, вход 512) из чекаута 3DDFA-V3, пять точек — POS-выравнивание upstream. YuNet (OpenCV) не находил плотные портреты, где лицо занимает больше ~70% кадра (скор 0.61 при пороге 0.7); RetinaFace на том же кадре даёт 0.999. Цена — ~3.7 с на кадр вместо ~0.5 с, поэтому счёт идёт на секунды, а окно статуса показывает прогресс. Порог уверенности — `configs/runtime.yaml: detector_confidence`, он входит в ключ кэша. Если лица нет в кадре, обработка падает с явной ошибкой; режим «Готовый кроп 224×224» обходит детектор.

### Фототекстура и тепловая карта

- Переключатель **«Фото»** использует пиксели исходного снимка и UV, рассчитанные по проекции реконструированного 3DDFA mesh для каждого vertex. Это не альбедо 3DMM и не синтетическая заливка. Источник полноразмерный; топология по-прежнему ограничена 35 709 вершинами.
- Карта включена по умолчанию: расстояние, α_id shape или normal displacement относительно первого, предыдущего или указанного кадра. Перцентиль, пороги, палитры, гамма, прозрачность, сглаживание.
- `ldm68/106/134` — независимые слои **одного 3DDFA_V3**, не три разных модели.
- Без WebGL включается CPU PNG-рендер с geometry, теплокартой, статистикой, landmarks, орбитой и масштабом; до 6 кадров/с. **Вместо UV-текстуры CPU fallback переносит то же запечённое фото на вершины** (`server/rendering.py:_source_photo_vertex_colors` — выборка из того же атласа в цвет 35 709 вершин), поэтому фото видно, но с разрешением сетки, мягче WebGL-текстуры. 3D-cluster без WebGL помечается как XY.

### Таймлайн, кластеры и ракурсы

- Метрики находятся в самостоятельной таймлайн-ноде с датами, дорожками и значениями/robust MAD z/Δ предыдущему. Текущий кадр в этой ноде подчёркнут в строке «Дата / кадр» и именно он даёт число справа от дорожки (наведение на число пишет, кадру или паре оно принадлежит); вертикальную линию-плейхед здесь не рисуем — она только засоряет графики. Плейхед живёт в полосе кадров 3D-панели и перетаскивается: берутся за метку на верхнем крае линии, позиция считается по ломаной маршрута, а выход за её границы переключает пару под пальцем (как клик по промежутку между кадрами). Стрелки ←/→ на метке шагают по кадрам маршрута, слайдер «% перехода» двигает тот же курсор.
- Верхний график нода считает сервер (`/api/chart/series` по вершинам меша); дорожки реестра — слой под ним. Пока выбор не троган вручную (`visibleMetrics: null` в воркспейсе), слоем показываются все метрики реестра, у которых есть значение хотя бы на одном кадре текущей группы. Отметка или снятие любой галки в «Дорожки» переключает слой на ручной список, «Сбросить» возвращает автовыбор, а пустой вручную снятый слой остаётся пустым.
- Если автовыбору нечего показывать, слой говорит причину из тех же строк, что и значения (например, «23 метрик реестра: ракурс вне профилей или метрика выключена»), а не молчит пустой рамкой.
- PCA, UMAP, t-SNE используют кэшированные параметры **α_id**; seed, расстояние, K-means, 2D/3D. Вычисление/интерполяция явно помечаются.
- Нода «Облако α_id» открывается в режиме **«Сравнение»**: только выбор расстояния, порог похожести, матрица попарных расстояний с подсветкой пар ниже порога и подписью строк (номер ↔ дата кадра). Всё остальное — метод проекции, размерность, кластеры, цвет — живёт в режиме **«Облако»** и по умолчанию скрыто, потому что на вывод «похожи ли» не влияет. Порог не откалиброван: α_id описывает форму лица, а не идентичность; диапазон порога свой для косинусного (0…0.5) и евклидова (0…10) расстояния, при смене метрики он сбрасывается на разумный.
- 5 профилей yaw/pitch/roll редактируются по отдельности. Ручные углы у фото имеют приоритет над автоматическими.
- Ракурс 3D-сцены берётся от углов наклона головы активного фото (кнопка **«Ракурс с фото»**, по умолчанию включена): модель поворачивается на yaw/pitch/roll с тем же порядком осей `Rz·Ry·Rx` и тем же знаком, что в `server/rendering.py:rasterize` и `configs/pose_profiles.yaml` (положительный yaw — нос вправо на снимке). Пресеты вида (`Фронт / −35° / +35° / Профиль`) больше не двигают камеру, а добавляют поворот модели к углам фото; в морфе углы интерполируются вместе с мешем. Текущие углы показаны в подписи над вьюпортом. CPU fallback получает те же yaw/pitch, но roll игнорирует — как и серверный рендер.

### «Глаза»: измерение и качество, а не аутентификация

MediaPipe Face Landmarker на CPU даёт 478 landmarks, включая 10 iris points; на исходном фото видны и редактируются все ключевые точки. Рядом с бирюзовым контуром MediaPipe рисуется **пунктирный лиловый контур глазной щели от 3DDFA_V3** — шесть точек `ldm68 36:42 / 42:48`, спроецированных в пиксели фото тем же путём, что и запекание текстуры (`server/models/tddfa.py:photo_uv` через `alpha` и `alignment` реконструкции, кэш `cache/<id>/ocular-mesh.json`). Стороны назначаются по положению на изображении, а не по соглашению нумерации, поэтому «Слева на фото» означает один и тот же глаз для обеих моделей. Для каждого глаза показаны две пары чисел: ширина/высота щели и `D/H` по MediaPipe и по 3DDFA. Для записи можно задать обезличенный comparative cohort `A/B/C`, ввести углы из своей таблицы, явно проверить gaze и отметить ручную разметку; 20 формул доступны в панели, CSV и реестре метрик.

**Отбора кадров нет.** В выборку попадает каждый кадр, для которого посчитаны измерения, а метрики реестра публикуются независимо от ракурса и от отметки «проверено» (`server/analysis.py`). То, что раньше называлось `exclusion_reasons`, теперь `quality_flags`: признаки (`Ракурс вне анфасного окна…`, `Радужка перекрывает прорезь: D/H = …`, `Мелкая разметка…`, смещение зрачка, blendshape моргания) — это описания чисел, а не причина выбросить кадр. `frontal_score` превышениями углов и смещением зрачка служит только порядком списка; штраф за разрешение из него убран. Ключ `eligible` сохранён как константа `true` ради CSV и старых закладок UI.

Это **видимые двумерные проекции мягких тканей**, не измерение костей. В корпусе есть фото с реалистичными масками, закреплёнными за веко: у них прорезь сужена намеренно, поэтому `D/H > 1` и расхождение двух контуров — предмет сравнения, а не брак разметки. Кольцо 3DDFA — шаблонная окружность вокруг глазного яблока (у BFM нет геометрии век), оно не повторяет край ресниц, но независимо подтверждает ordering: на всех пяти кадрах обе модели дают минимальный `D/H` на `1999_09_01` (1.41 против 1.34) и максимальный на `2024_03_02` (1.81 против 1.79). Ошибка точки и ракурс существенно влияют на узкие щели. Метрики, группы и α_id не доказывают личность, наличие накладки/маски или естественность.

## Метрики и расширение

### Один новый Python-файл

Скопируйте `docs/examples/mesh_height.py` в `metrics/tddfa_v3/mesh_height.py` и нажмите «Обновить» в реестре. Метрика появляется в списке и, при стандартном выборе дорожек, на графике без правки React.

```python
from server.registry import metric
import numpy as np

@metric('my_height', 'Высота реконструкции', model='3ddfa_v3', unit='IOD₀', inputs=('vertices',))
def compute(ctx):
    return np.ptp(ctx['vertices'][:, 1])
```

В контексте 3DDFA: `vertices` (ID+exp), `identity` (без exp), `albedo`, `alpha`, `ldm68`, `ldm106`, `ldm134`. Геометрия — в общей канонической системе, в масштабе среднего шаблона IOD₀. Все значения на исходных кадрах считаются Python-функциями, не нарисованы в браузере.

В декораторе можно указать `poses=('frontal', 'three_quarter_left')`. YAML переопределяет включение, заголовок/единицы и warn/alert отдельно для каждого профиля:

```
configs/metrics/3ddfa_v3/frontal.yaml
configs/metrics/3ddfa_v3/three_quarter_left.yaml
configs/metrics/3ddfa_v3/three_quarter_right.yaml
configs/metrics/3ddfa_v3/profile_left.yaml
configs/metrics/3ddfa_v3/profile_right.yaml
```

Для `mediapipe`, `fan`, `adaface` существуют pose-specific YAML по пяти профилям. MediaPipe реально выдаёт точки; 20 геометрических глазных показателей описаны отдельно в `server/ocular.py`. Только две из них подключены к метрическому timeline, где остаются `null` до прохождения quality-filter и ручной проверки. FAN/AdaFace не вычисляются.

Робастный z: `(x−median)/(1.4826·MAD)`, отдельно по группе и ракурсу. При n<3/нулевом MAD недостоверная оценка не выдумывается. Метрика вне разрешённого ракурса даёт пустое значение с объяснением.

### Профиль ракурса

Диапазоны пяти текущих профилей редактируются в ноде и в `configs/pose_profiles.yaml`. Добавление шестого пока намеренно запрещено валидатором (требование — ровно пять); для расширения количества меняется эта проверка и список метрик нового профиля. Основные списки строятся по данным.

### Следующая модель

Граница адаптера описана в `server/models/base.py`; план моделей и ожидаемые ключи — `configs/models.yaml`. Реализуйте адаптер с версией/хэшами весов и явными координатами; добавьте его в последовательный pipeline `server/storage.py`, расширьте создание metric context в `server/analysis.py` и доступность `/api/models`. Признаки модели храните независимо, не инвалидируя 3DDFA. Для новых оверлеев понадобится вернуть настоящие точки в общей системе и добавить управление ими. 2D-точки нельзя выдавать за измеренные 3D. Автоматическое появление **метрик** уже реализовано; автоматическое подключение произвольной новой **модели** — отдельная интеграция.

## Границы первого этапа

### Quick start on the canvas
The dismissible **Быстрый старт** card links directly to the photo source, 3D scene, and metrics timeline. It reports the current photo/cache counts and can be dismissed without changing the saved workspace. Reopen onboarding by clearing the browser's `atlas-guide-dismissed` localStorage key.

### Canonical UV photo texture
The WebGL viewer now bakes the source photo into the original 3DDFA template UV atlas triangle by triangle and retains the model's canonical UV coordinates. Per-photo atlases are lazy and cached in `cache/{photo_id}/`; source pixels outside the projected face remain unobserved rather than being clamped to image borders. This adapts the affine UV-baking approach in the linked `uv_module` project. Beauty-fill and synthetic symmetry content are not used for analysis.

### Optional mesh-noise calibration
In 3D heat-map settings, open **Калибровка шума меша** and assign 2–3 ready non-demo views to each of seven participants. A per-vertex within-participant repeatability threshold is computed and can be subtracted from geometric distance heat values (values floor at zero). It does not affect α_id or normal displacement. This is an empirical repeatability baseline, not pure model error; pose, expression, image quality, and real variation may contribute. Raw uncorrected heat remains available. The current local library does not contain the required seven-person sample, so calibration must wait until those photos are imported.
