# 01 — Stage 2 contract

Это первый и самый базовый тест.

Его смысл — проверить, что директория Stage 2 в текущем прогоне
структурно пригодна для дальнейшего анализа.

Теперь этот тест даёт не только набор ошибок и предупреждений,
но и итоговый статус этапа:
- `PASS` — можно двигаться дальше к следующему тесту;
- `BLOCKED` — этап считать пройденным нельзя.


## Что именно проверяется


### 1. Поиск артефактов

Скрипт принимает путь к корню Stage 2 и не требует,
чтобы все файлы лежали строго на одном уровне.

Он рекурсивно ищет JSON и CSV в пределах заданной глубины,
а затем пытается определить кандидатов на:
- manifest;
- photo metrics;
- pair metrics;
- zone metrics;
- timeline CSV.

Это сделано для того, чтобы тест был применим к реальной структуре прогона,
а не только к идеальному контракту имени файлов.


### 2. Базовая структура и читаемость

Для найденных артефактов проверяется:
- что файл существует и не пуст;
- что JSON парсится;
- что CSV читается и имеет заголовок;
- что главные JSON не выглядят повреждёнными.

Битый JSON или CSV — это `ERROR`.


### 3. Проверка schema

Если у manifest / photo / pair / zone JSON есть поле `schema`,
оно сравнивается с ожидаемым значением:
- `deeputin-stage2-v1.4-robustness`

Несовпадение schema — `WARN`, а не автоматический блокер,
потому что возможен старый прогон. Но такое предупреждение
обязательно надо учитывать при дальнейшей интерпретации.


### 4. Извлечение записей

Скрипт пытается извлечь массивы записей из типичных полей:
- `data`
- `rows`
- `items`
- `pairs`
- `photos`
- `zones`

Если файл найден, но записи из него извлечь нельзя,
это уже `ERROR`, потому что следующий тест на такие данные опереться не сможет.


### 5. Минимальная связность сущностей

Если удалось извлечь записи:
- у photo records должны быть уникальные `photo_id`;
- у pair records должны быть уникальные `pair_id`;
- если в pair record есть ссылки на photo A / B,
  они должны указывать на существующие `photo_id`.

Дубли идентификаторов — `ERROR`.
Ссылка пары на несуществующее фото — `ERROR`.
Отсутствие очевидного ID-поля — `WARN`, потому что контракт может отличаться,
но это уже сигнал, что следующий тест потребует адаптации.


### 6. Пустые записи

Пустые или бессодержательные записи логируются как `WARN`.
Если их окажется много, это уже повод отдельно обсуждать,
почему файл формально читается, но фактически пуст по содержанию.


## Когда этап считается пройденным

Итоговый статус `PASS` ставится только если одновременно выполнено всё ниже:
- нет `ERROR`;
- найден и прочитан manifest;
- найден и прочитан photo metrics JSON;
- найден и прочитан pair metrics JSON;
- проверено больше нуля файлов;
- извлечено больше нуля photo records;
- извлечено больше нуля pair records.

Если хотя бы одно из этих условий не выполнено,
итоговый статус будет `BLOCKED`.

Именно `PASS` у этого теста означает,
что по структурному контракту Stage 2 можно идти дальше.


## Формат результата

Пример:

```text
WARN code=SCHEMA_MISMATCH subject=/path/to/pair_metrics.json detail=schema=old-version expected=deeputin-stage2-v1.4-robustness
SUMMARY script=check_stage2_contract status=PASS checked_files=7 errors=0 warnings=1 photos=1909 pairs=305 zones=567
```

Или при блокировке:

```text
ERROR code=PAIR_METRICS_NOT_FOUND subject=/path/to/root detail=pair metrics JSON not found
SUMMARY script=check_stage2_contract status=BLOCKED checked_files=2 errors=1 warnings=0 photos=0 pairs=0 zones=0
```


## Что пока не входит в этот тест

В этот первый тест специально **не** входят:
- научная проверка корректности метрик;
- анализ калибровки;
- валидность chronology flags;
- FDR;
- evidence;
- Stage 2B / Stage 3.

Это всё будет отдельными тестами дальше.


## Интерпретация результата

- `status=PASS` — можно переходить к следующему тесту.
- `status=BLOCKED` — двигаться дальше как будто этап проверен нельзя.
- `WARN` при `PASS` не блокируют следующий шаг,
  но их надо учитывать как ограничения доверия.
