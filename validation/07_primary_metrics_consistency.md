# 07 — Первичные метрики

**Статус:** предварительная заготовка.

## Назначение

Проверяет согласованность ldm134, identity-only, dense mesh и pose leakage без попытки свести их в один искусственный балл.

Этот тест запускается только после успешного `PASS` предыдущего шага.
Он не должен делать окончательных научных выводов; его задача — проверять
конкретные инварианты и выдавать короткие диагностические сообщения.

## Входы

- `stage2_root` — путь к входу.

## Уровни результата

`ERROR` блокирует переход дальше. `WARN` не блокирует автоматически,
но переносится в обсуждение результатов. `PASS` означает только то,
что проверяемые инварианты этого теста не нарушены.

## План проверок

Сначала проверяются наличие и читаемость входов, затем структура и связи,
после чего — содержательные условия, специфичные для этого этапа.
Для повторяющихся проблем выводятся только первые примеры и агрегированный
счётчик; успешные записи не печатаются.

## Критерий готовности

Черновой скрипт специально завершает работу с предупреждением
`SCAFFOLD_ONLY`. После получения реального лога предыдущего теста и
уточнения фактических имён полей этот TODO заменяется строгими проверками.

## Команда запуска

```bash
python3 validation/check_primary_metrics_consistency.py <stage2_root>
```

## Ожидаемый компактный формат

```text
WARN code=SCAFFOLD_ONLY subject=check_primary_metrics_consistency.py detail=specific checks are not implemented yet
SUMMARY script=check_primary_metrics_consistency.py status=PASS checked_inputs=1 errors=0 warnings=1
```

Такой `PASS` пока **не является основанием** переходить дальше: это
технический каркас, а не законченная проверка.


## Что уточнить после первого реального запуска

После первого запуска этого теста разработчик должен дописать сюда фактические наблюдения:
- реальные входные файлы;
- реальные имена полей;
- какие WARN оказались ожидаемыми для формата;
- какие случаи надо перевести в ERROR;
- какие дополнительные компактные артефакты стоит читать вместо тяжёлого полного набора данных.

- Какие поля в реальном output соответствуют ldm134_rmse, ldm134_p95, identity_only_ldm134_rmse и identity_only_motion_rmse.
- Какие конфликтные сочетания метрик считать merely suspicious, а какие явно ошибочными.
- Какие secondary channels допустимо использовать только как corroboration, а не как primary evidence.

## Подсказка разработчику

Не расширяй скрипт до полного пересчёта Stage 2/2B/3. Смысл validation-слоя —
проверять инварианты и согласованность уже записанных результатов, а не запускать
тяжёлую аналитику заново. Если для проверки не хватает лёгкого агрегата,
сначала зафиксируй это в markdown и только потом добавляй новый компактный derived artifact.
