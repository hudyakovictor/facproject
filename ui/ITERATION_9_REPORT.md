# Iteration 9 — Patch Safety Lifecycle

## Итоговая готовность после итерации: 72/100

Эта итерация выбрана по методу 20/80: из открытого backlog (Timeline/Replay, Calibration/Metrics, 3D Inspector, Interface Contract, Performance/Security — все декоративные или второстепенные) она даёт наибольший риск-снижающий эффект с наименьшим объёмом кода, потому что закрывает единственный путь, которым автоматизация могла реально сломать `app6` без предупреждения.

## Что сделано

1. **Изолированный apply.** `run_isolated_patch()` создаёт одноразовый `git worktree` от `HEAD`, применяет присланный diff только там и никогда не трогает реальное дерево первым.
2. **Обязательный авто-тест перед касанием реального дерева.** В изолированном worktree запускается вызывающим переданный `test_cmd` (в API — регрессионный раннер `app6-regression` из `runners.yaml`). Тест обязателен и синхронный, не «по желанию».
3. **Условный real-commit.** Реальный `app6` и настоящий git-commit создаются **только** если изолированный тест-прогон завершился успешно. Перед этим создаётся файловый backup (как в Iteration 8), затем патч применяется к реальному дереву и коммитится с явным `-c user.email/user.name`.
4. **Гарантия отсутствия побочных эффектов при провале.** Если apply-check, apply или тест-прогон в изоляции провалились — функция возвращает структурированный результат (`passed`, `error`, `test_output`) и реальное дерево остаётся нетронутым; `finally`-блок всегда удаляет временный worktree (`git worktree remove --force` + `shutil.rmtree`), даже при исключении.
5. **Безопасный rollback.** `revert_patch_commit()` делает `git revert --no-edit <sha>` вместо восстановления файлов из бэкапа — сохраняет историю и явно виден в git log; при конфликте revert корректно прерывается (`git revert --abort`) и поднимается ошибка.
6. **Новые API-роуты**: `POST /api/patches/apply-safe`, `POST /api/patches/{sha}/revert` в `main.py`, использующие спецификацию раннера `app6-regression` для построения команды теста.

## Найденный и исправленный реальный баг

В процессе написания тестов для изолированного пути обнаружился скрытый баг, который также присутствовал в исходной (Iteration 8) функции `apply_patch`: **`git apply`, вызванный с `cwd`, указывающим на подкаталог репозитория (а не на его корень), может тихо напечатать `Skipped patch '<file>'` и вернуть код `0`, не изменив ни одного файла и не сообщив об ошибке.** Это воспроизводится как в обычном рабочем дереве, так и в linked `git worktree`, когда `allowed_root` (в проде — `app6_root`) не совпадает с корнем репозитория — именно так устроено в реальном проекте (`app6` — подкаталог `/data/dddeputin`, а не сам репозиторий).

Исправление: обе функции (`apply_patch` и `run_isolated_patch`) теперь всегда запускают `git apply`/`git apply --check` **из корня репозитория** с флагом `--directory=<путь до allowed_root относительно корня>`, а не через `cwd`, указывающий на подкаталог. Это надёжно воспроизводимо в проверках и устраняет источник тихого no-op применения патча.

Этот баг не проявлялся в тестах Iteration 8, потому что тестовые фикстуры там всегда делали `allowed_root == repo root` — то есть тестировали сценарий, который отличается от реальной прод-конфигурации. Новые тесты Iteration 9 воспроизводят реальную структуру (`app6/` как подкаталог) и поэтому этот баг обнаружили.

Попутно найден и исправлен второй баг: `revert_patch_commit` падал с ошибкой git «Author identity unknown», потому что не передавал `-c user.email/user.name`, как это делает шаг commit — исправлено аналогично.

## Честные ограничения (не преувеличиваем готовность)

- Изолированный путь проверен **только на синтетических temp-git фикстурах** внутри модульных тестов — не через реальный HTTP API, не через UI, и не на настоящей истории `app6`.
- `run_isolated_patch` не покрыт тестом на «apply прошёл в изоляции, но упал на реальном дереве» (гонка/расхождение состояний) — такой сценарий помечен `RuntimeError` в коде, но не имеет отдельного unit-теста.
- Нет UI-элемента для запуска `apply-safe`/`revert` — это оставлено как мелкая доработка для дальнейшей итерации, согласно приоритету «сложное сейчас, мелкое потом».
- Нет commit/tag lifecycle для *серии* патчей (несколько патчей подряд, тегирование релизных точек) — это отдельная, менее рискованная задача, оставлена в backlog.
