### 1.2 Ошибки API маскируются под нехватку данных (A104, A116)

```
HTTP 500 → PairAnalysisPage → «Парное сравнение недоступно: API не вернул минимум две записи»
```

Причина — сращивание условий в одну ветку:

| Файл | Строка | Код |
|---|---|---|
| `PairAnalysisPage.tsx` | 14 | `if (q.isError \|\| !a \|\| !b) return <…>Парное сравнение недоступно: API не вернул минимум две записи</…>` |
| `MorphingPage.tsx` | 13 | `if (q.isError \|\| !photo) return <…>Морфинг недоступен: API не вернул Stage 2</…>` |
| `CalibrationPage.tsx` | 9 | `if (q.isError \|\| !q.data) return <…>Калибровочный endpoint недоступен</…>` |
| `PhotoInspectorPage.tsx` | 16 | `if (query.isError \|\| !selected) return <State … error />` |
| `DataManagerPage.tsx` | 82 | `if (timelineQuery.error \|\| !activeRow) return <…>Не удалось загрузить реальные данные Stage 2</…>` |

Пять из шести страниц с обработкой ошибок склеивают `isError` и «пусто». Диагностируемость нулевая: причина (таймаут, 500, 409, пустой массив) не показывается никогда. Только `TimelinePage:96` и `OverviewPage:35` печатают `String(error)`.

### 1.3 `null` как достоверный ноль — подтверждено на DOM (A73)

Строка таблицы для фото с `quality: null, yaw: null`:

```
["1","p1","2020-01-01","2020","frontal","0.00","0°","","н/д","—"]
                                          ^^^^^^  ^^^
                                          null    null
```

`DataManagerPage.tsx:52` `qualityQ: p.quality == null ? 0 : p.quality * 100` и `:53` `yaw: p.yaw ?? 0`. При этом соседние колонки умеют показывать `н/д` и `—`, то есть механизм честного отображения в файле уже есть — он просто не применён к двум главным метрикам.

Позитивно: фильтр качества (A96) **не** отбрасывает фото с `quality: null` при пороге 0.5 — то есть в фильтрации `null` обрабатывается верно, а в отображении нет. Несогласованность внутри одного экрана.

## 2. Stage-1 режим: то, что пользователь увидит на самом деле

Ключевой факт, пропущенный в первом аудите: `/api/v1/timeline` (`server.py:202`) при отсутствии Stage 2 **не отдаёт ошибку** — он возвращает инвентарь Stage 1 через `stage1_timeline.build_stage1_inventory`. Это и есть штатное состояние проекта сегодня. Пробы A148–A152 прогнали UI на точной структуре строки из `stage1_timeline.py`.

### 2.1 Интерфейс подписывает Stage-1 данные как Stage-2 (A148, A150, A153)

```
TimelinePage → «ТАЙМЛАЙН · STAGE 2 · РЕАЛЬНЫЕ ДАННЫЕ · 2 фото · 1999—2003»
OverviewPage → «Данные загружены из Stage 2 через /api/v1/timeline; это не вердикт»
```

Оба поданы на `analysis_stage: "stage1_inventory"`. API честно помечает стадию — **UI не читает поле `analysis_stage` ни разу**. Единственное место, где `analysisStage` вообще используется, — `DataManagerPage:46` (`noSidecar`) и `AuditLogPage` (печатает значение). Ни один экран не меняет заголовок, не блокирует метрики и не предупреждает.

Иронично: сам ответ содержит поле `note: "Реальный инвентарь Stage 1: сравнительные метрики… появятся только после Stage 2"`, и Overview его даже отображает — прямо под собственным утверждением про Stage 2 (A150). Два взаимоисключающих сообщения в одном экране.

### 2.2 Технический маркер превращается в «находку» (A152)

`stage1_timeline.py:68` кладёт `"flags": ["STAGE1_INVENTORY_ONLY"]` в **каждую** строку. `TimelinePage.tsx:16` и `TopBar.tsx:53` считают находкой любое фото с непустым `flags[]`.

```
2 фото Stage-1  →  «Находки · 2»
1909 фото Stage-1 → «Находки · 1909»
```

Счётчик находок, главный индикатор шапки, в текущем режиме показывает 100 % и бесполезен. Нужен список технических флагов-исключений.

### 2.3 Четыре обязательных поля отсутствуют в Stage-1 ответе (A144–A147)

| Поле в `ResearchPhoto` | Обязательное в TS | Есть в Stage-1 ответе |
|---|---|---|
| `evidenceState` | да (`string`) | **нет** |
| `stage2PairCount` | да (`number`) | **нет** |
| `stage2StatusCounts` | да (`Record<…>`) | **нет** |
| `stage2EvidenceCounts` | да (`Record<…>`) | **нет** |

Тип объявляет их не-опциональными, поэтому TS уверен, что они есть. В рантайме `Object.entries(photo.stage2StatusCounts)` (`TimelinePage:16`, `TopBar:53`) должен был бы бросить `TypeError`. Пробы A148/A152 показали, что падения нет — но лишь потому, что `flags.length > 0` в `||`-выражении срабатывает первым и короткое замыкание не доходит до `Object.entries`. **Это удача, а не защита.** Любое фото Stage-1 с пустым `flags[]` (или перестановка операндов при рефакторинге) немедленно уронит таймлайн.

### 2.4 Сигналы честности от API не доходят до экрана (A151)

Ответ содержит:

```json
"ui_fields_schema": "deeputin-ui-fields-v1.0",
"ui_fields_complete_photo_count": 0,
"ui_fields_violations_by_field": {"boneScore": 1909, "p0": 1909, "p1": 1909, "p2": 1909},
"uiContractViolations": ["boneScore","p0","p1","p2"]   // на каждой строке
```

Ни одно из этих полей не объявлено в `ResearchTimeline`/`ResearchPhoto` и не выводится. Проба A151: строка «boneScore» на экране появляется — но только из статичной подписи футера «Недоступные поля не подменяются: boneScore/p0–p2», захардкоженной в `TimelinePage`, а не из данных. Совпадение маскирует проблему: захардкоженный текст будет врать, как только набор нарушений изменится.
