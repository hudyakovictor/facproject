**M6. 🔴 Методологический конфликт: aligner стирает реальный масштаб — то, что вся экосистема запрещает.**

Следствие: (а) морфабельность/сходство измеряются на обезличенных от масштаба формах — два лица, различающиеся реальным размером черепа, станут «ближе», чем они есть; (б) все метрики (mean_dist, cosine по flatten, зональные дистанции) живут в безмасштабных единицах, а не в мм. Нужен осознанный выбор: два режима (identity-only: масштаб стёрт; size-inclusive: масштаб сохранён, метрики в мм) — и честная подпись в UI, какой показан (M). Дополнительно: магические константы `0.15` (порог морфабельности, продублирован в 4 местах: `server.py:95,190,227`, `App.jsx:88` и в `ZoneScoresPanel` `App.jsx:486`) и `0.025` (`App.jsx:74`) не откалиброваны по данным — лечится в M10.

## Часть B. Разбор предложенных фич — по одной (M7–M20)

**M7. 🧬 Multi-Face Blend (3–4 лица, барицентрический слайдер) — P1, M–L.**
Правильная новость: топология общая, поэтому V = Σ wᵢVᵢ — это всего лишь N позиционных атрибутов в шейдере. План: (1) backend `POST /api/morph-multi` — N файлов, N реконструкций, ответ = triangles/uv **один раз** + verticesᵢ + textureᵢ (см. M21 про сжатие); (2) шейдер: `attribute vec3 positionC; attribute vec3 positionD;` + `uniform vec4 u_weights;` — `morphedPos = position*w.x + positionB*w.y + positionC*w.z + positionD*w.w` (лимит 4 лиц = 4 атрибута, у WebGL их запас есть); (3) UI: для 3 лиц — треугольный барицентрический пикер (x,y точки внутри треугольника → нормированные w), для 4 — тетраэдр (2D-проекция + слайдер глубины, честный UI заметно сложнее — рекомендую начать с треугольника); (4) live-метрики обобщаются попарно (популярная пара → max дистанций). Поправка к «нигде в open source подобного нет»: мульти-изображный морфинг существует (FaceMorpher, webmorph.org и др. усредняют N лиц), но **интерактивный барицентрический UI + forensic-метрики по зонам** — действительно редкое сочетание; уникальность в подаче, не в математике.

**M8. 🎬 Timeline-цепочка A→B→C→D (Catmull-Rom) — P1, M.**
Ключевой выбор: интерполировать **в пространстве формы α_id (80-мерный вектор BFM)**, а не вершин: α-путь гладкий по построению (форма = линейная функция α), Catmull-Rom по 80 числам дешевле и стабильнее, чем по 107 127 координатам, и траектория остаётся внутри многообразия лиц (почти — см. M15 про экстраполяцию). Формула сегмента: `α(u) = 0.5·[(2P1) + (−P0+P2)u + (2P0−5P1+4P2−P3)u² + (−P0+3P1−3P2+P3)u³]`. Реализация: (а) точная — бэктенд считает keyframes-мешей K штук (K=8–12) один раз, фронт интерполирует **α** на CPU в rAF и пересобирает position-буфер (35 709×3 float — пересборка ~1 мс, приемлемо); (б) грязная, но мгновенная — Catmull-Rom прямо в вершинном шейдере по 4 позиционным атрибутам (для 4 лиц). UI: таймлайн с перетаскиваемыми keyframes (позиция = порядок), playhead = t. Совместимо с M7 (цепочка — частный случай). Textures: кросс-фейд по тем же весам.

**M10. 📐 Morphability 2.0: настоящая калибровка вместо магии 0.15 — P1, M.**

План: (1) бэктенд при старте (или по команде) читает Stage 1 выводы app8/stage1 (формат совместим — M29), считает σ по тем же позовым бинам; (2) morphability = `Φ(−z)`, где `z = (d − median)/σ` — процент «похожести» становится вероятностно осмысленным: «дистанция внутри same-day шума» = ~50%+; (3) константа 0.15 остаётся фолбэком с пометкой `uncalibrated`; (4) порог `0.025` для % вершин тоже заменить на `k·σ` (k=2); (5) предупреждение «морфинг будет некачественным» при z > 3. **M14. 🌊 ARAP/TPS-деформация — P4, L; честный pushback.**
Для **same-topology** мешей (наш случай: оба лица — вершина-в-вершину BFM) линейная интерполяция не порождает складок и самопересечений: смещения после канонического выравнивания малы и когерентны, плотное соответствие исключает склейку. ARAP решает проблему деформации **разной** топологии/больших смещений — её тут нет. Реальная польза была бы: (а) текстурный варпинг при несовпадении UV (не наш случай — UV общий); (б) морф между app6-сеткой и app8-сеткой (разные пространства) — тогда TPS через `scipy.interpolate.RBFfittter`-класс достаточно, open3d/igl (тяжёлые бинарные зависимости) не нужны. Вердикт: не включать в дорожную карту до появления межтопологической задачи; если очень хочется «физичности» — дешёвая альтернатива: нормал-пересчёт по t (`computeVertexNormals` промежуточных кадров) или shade-коррекция в фрагментном шейдере, эффект «кожа дышит» за 20 строк.

**M15. 🔭 4D Age Progression — P3, L; полезен, но это иллюстрация, не прогноз.**

Обязательные меры по стандартам самого проекта: маркировка `exploratory/synthetic` в UI и в экспорте (принцип E10 `provenance: real|synthetic`), отображение доверительной полосы (bootstrap по остаткам регрессии — `stats.bootstrap_ci` уже написан в stage2_v2!), запрет экстраполяции дальше 0.5·span выборки без явного клика «я понимаю». API: `POST /api/morph-sequence` (N фото + years[]), ответ = keyframes α-траектории + метаданные тренда (скорость изменения по зонам = мостик к M19). Рендер: таймлайн M8 переиспользуется полностью.

**M16. 🔑 Identity Decomposition — P1, S–M; максимум эффекта на вложенный день.**
Красота идеи в том, что **V_mean у вас уже есть**: это форма при нулевых коэффициентах 3DMM (`compute_shape(zeros)` — один вызов бэктенда; в терминологии app8 — «среднее лицо модели»). План: δ_A = V_A − V_mean, δ_B = V_B − V_mean; шейдер получает атрибуты `position` (=V_mean), `deltaA`, `deltaB` и `uniform vec2 u_tA_u_tB`; `V = V_mean + t_A·δ_A + t_B·δ_B`; при `t_A=1+t_B=1` получаем линейный морф — то есть текущий режим вкладывается бесплатно, плюс новые: «оба лица минус общее», «только уникальность B». UI: три слайдера + режим теплограмм |δ_A|, |δ_B| (вершинный varying по норме дельты — палитра уже есть в `getHeatmapColor`). Аналитическая ценность: разделяет «что общее у обоих» (отклонение mean) и «что уникально каждому» — в вашем Usecase «какую долю уникальности A сохраняем» звучит точно. Согласуется с доктриной: это измерение, не вердикт.

**M18. 🌗 UV Diff — P1, S; самый дешёвый режим из всего списка.**
Фрагментный шейдер, ~10 строк: третий режим `u_showUVDiff`: `vec3 d = abs(texA.rgb − texB.rgb); float m = max(max(d.r,d.g),d.b);` → через ту же палитру `getHeatmapColor(m·scale)`. Показывает разницу пигментации/морщин/текстуры кожи независимо от формы — ваша формулировка верна. Нюансы: (1) каноническое UV совпадает (общая развёртка) — дифф корректен по построению; (2) освещение/тone в uv_module может вносить общий сдвиг яркости — добавить «percentile-нормализацию» m по 95-му перцентилю (считать на бэктенде при загрузке текстур, отдать scale в metadata); (3) отдельно подсветить зоны, где текстура не определена (швы развёртки) — alpha-канал текстур. UI: четвёртый чекбокс в «Слоях» + вкладка «Texture diff».

**M19. 🌊 Temporal Identity Drift — P3, L; это stage2_v2 в миниатюре.**
Содержательно: дрифт α_id по годам = то, что основной пайплайн делает по вершинам с FDR и шумовым полом (`stats.cusum` уже ловит «медленный дрейф, невидимый попарным сравнением» — прямое соответствие вашей идее «отклонение от прямой траектории — аномалия»). Правильная архитектура: не дублировать, а **переиспользовать**: бэктенд-эндпоинт `/api/drift` принимает N фото+даты (или читает Stage 1 выводы), считает α-траекторию, остатки от линейной регрессии, флагует |остаток| > 2σ̃; UI: временная ось + 3D-подсветка зон max-девиации (зоны из M13). Но: интерпретация «скорость биологического старения vs хирургических изменений» — вне компетенции модели (3DMM не различает причины) — переформулировать как «отклонение от линейного тренда формы» без причинных слов (снова M13/M24). Зависимость: M29 (чтение Stage 1) либо честный mульти-аплоад.

**M20. 🪞 Анализ симметрии — P2, M; с одной важной оговоркой.**
Реализация чисто numpy: (1) срединная плоскость = x=0 (после канонического выравнивания оси уже стандартны); (2) зеркало: V_m = V с x→−x; (3) соответствие: `scipy.spatial.cKDTree(V_m).query(V)` (первое легитимное появление scipy в morphing — лёгкая зависимость, M27); (4) асимметрия вершины a_i = ‖V_i − V_m(соответствующего i)‖; зональные scores по атласу (M13); (5) heat-карта по вершинам — готовый механизм varying'а из M16. Каверка, которую надо сказать вслух: BFM — статистическая модель, в которой асимметрия частично «замыта» усреднением выборки (формы почти симметричны по построению), а identity-only канал `v_id` ещё и реконструирован моделью — реальная асимметрия лица частично не доходит до меша. Поэтому score измеряет асимметрию «модель+личность» и обязательно валидируется: same-фото против зеркальной пары, известные асимметричные случаи. Судебный вывод «хирургическая асимметрия» из этого числа — нельзя (M24). Procrustes поверх соответствия — да: `stage2_v2/geometry.trimmed_kabsch` переиспользовать (numpy, уже написан).

## Часть C. Кросс-проблемы внедрения (M21–M30)

**M21. 📦 Payload-архитектура для N лиц — блокер для M7/M8/M12/M15 — P1, M.**
Сейчас 2 лица ≈ 5–10 МБ JSON (M5); 4 лица наивно → 15–25 МБ. План по убыванию выигрыша: (1) **triangles и uv_coords — один раз** (топология общая — это уже так, но продублируйте осознанно в схеме ответа: `topology: {triangles, uv}`, `faces: [...]`); (2) бинарная кодировка массивов: `Float32Array → base64` (×3.5–4 экономии против text-floats: 4 байта+накладные против ~9 символов) или, лучше, `ArrayBuffer`-ответы отдельными эндпоинтами (`/api/morph/{id}/vertices.bin`) c JSON-манифестом; (3) `GZipMiddleware` — одна строка, −70% на текстовом JSON; (4) текстуры: WebP вместо PNG (uv_module умеет, cv2.imencode('.webp')) −40–60%; (5) previews удалить (M4). Итог на 2 лица: 5–10 МБ → ~2–3 МБ; на 4 лица — приемлемые ~5 МБ.

**M22. 🎮 GPU-архитектура мульти-морфа и таймлайна — P1, M (вместе с M7/M8).**
Один материал — все режимы: attributes `position(=A)`, `positionB`, `positionC`, `positionD`, `deltaA`, `deltaB` (M16); uniforms `u_mode` (0=pair linear, 1=barycentric, 2=catmull, 3=decomposition), `u_weights[4]`, `u_tA_u_tB`. Вершинный шейдер ветвит по `u_mode` (ветвление по uniform дёшево). Catmull-Rom в шейдере — 4 контрольные точки-атрибута + `u_segT` (позиция в сегменте) — покрывает цепочку из 4 лиц без пересборки буферов; для >4 лиц — режим keyframes с пересборкой position на CPU (M8а). Нормали: `computeVertexNormals()` на CPU при смене keyframe-кадра — иначе освещение «замораживается»; для линейного режима достаточно `mix(normalA, normalB, t)`+normalize в шейдере (добавить атрибут normalB). Лимит: 16 атрибутов — мы используем ≤9, запас есть.

**M23. 🌐 API-дизайн v3 — P2, S–M.**
Один `api_router` с версией (`/api/v3/...`), Pydantic-модели ответа, поле `schema: "deeputin-morphing-v3"` в каждом ответе (обычай проекта), эндпоинты: `morph-multi`, `trajectory` (N фото+years), `drift`, `face-space` (PCA/датасет, read-only из Stage 1), `mean-face` (кэшируемый), `calibration` (σ из M10, с полем `source: same_day_null_v1|fallback_constant`). Ошибки — структуры `{code, detail}` вместо строк. OpenAPI уже бесплатно. Плюс: вынести reconstruction-кэш по sha256 файла (повторная загрузка того же фото не должна пересчитывать torch) — LRU на 8–16 лиц.
