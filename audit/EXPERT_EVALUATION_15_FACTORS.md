## Детальный разбор по факторам

### Фактор 1: Pose bin isolation — **92/100** ✅
**Что требует ТЗ:** *«Сравнивать только внутри одного из 9 ракурсов»*

**Что в коде:**
- `pair_planner.py` формирует пары строго внутри `pose_bin`
- Cross-bin анализ только в `corroboration.py` — для подтверждения, не для primary score
- `unsupported_pose` и `inapplicable_pose` статусы для пар вне bins

**Что хорошо:** Жёсткая изоляция, нет утечки cross-bin в primary evidence.
**Что улучшить:** P1-14 (cross-bin corroboration не проверяет independence).

### Фактор 2: Axis gap control — **85/100** ✅
**Что требует ТЗ:** *«Per-bin yaw gap из pose_gate_v2.csv; для профиля ≤2°, фронтального ≤12°»*

**Что в коде:**
- `pose_policy_v3_9bins.csv` + per-bin thresholds
- `residual_tilt_limited` при >10° residual rotation

**Что хорошо:** Granular per-bin thresholds, не единый «всё >20°».
**Что улучшить:** P2-5 — `MIN_ALIGNMENT_QUALITY=0.5` не гейтит (D-003); residual_tilt gate добавлен, но не проверен на данных.

### Фактор 3: Bone priority — **48/100** ⚠️
**Что требует ТЗ:** *«Переносица, глазницы, скулы, подбородок — устойчивы; губы, крылья носа — меняются»*

**Что в коде:**
- `primary_zones.py` имеет `BONE_ZONES = {bridge, orbital_L/R, cheekbone_L/R, chin, jaw_L/R}` с весом 1.0
- `SOFT_ZONES = {cheek_soft, nose_wing, jaw_L/R}` с меньшим весом
- **НО** `core.py:365`: *«Nine reproducible coordinate zones; avoids unverified anatomical labels»*

**Проблема:** Код использует **координатную сетку** (x_low_low, x_low_mid...), а не анатомические зоны. Комментарий в `core.py:443-445` прямо говорит: *«Прежний комментарий называл их "bone zones", что противоречило самому коду»*. `primary_zones.py` декларирует анатомическую привязку, но она не верифицирована и не связана с координатными зонами.

**Что улучшить:** Нужна верифицированная карта: landmark_id → анатомическая зона.

### Фактор 4: Visibility intersection — **88/100** ✅
**Что требует ТЗ:** *«На профиле половина зон не видна; считать пересечение»*

**Что в коде:**
- `visibility_gate.py` считает `common_visible134` и `common_visible106`
- Fail-closed: <30/24 точек → пара исключается
- Profile-specific visibility из mesh topology

**Что улучшить:** `quality_zones.npz` не пишется (P1-17) — per-zone visibility texture отсутствует.

### Фактор 5: Date provenance — **90/100** ✅
**Что требует ТЗ:** *«Датировка по имени файла как единственный авторитет»*

**Что в коде:**
- `parse_photo_name()` → `YYYY_MM_DD[_N]` — обязательный формат
- `date_provenance` в info.json: `filename_only` / `corroborated` / `conflict`
- Конфликт → `date_provenance_limited` → evidence downgrade

**Что улучшить:** P1-15 — 100% кадров `filename_only` (нет corroborating EXIF). Механизм готов, данных нет.

### Фактор 6: Duplicate detection — **87/100** ✅
**Что требует ТЗ:** *«Побайтовые дубли отбрасываются; перцептивные помечаются»*

**Что в коде:**
- Stage 1: MD5 content hash → полный дубликат → skip
- dHash perceptual → near-duplicate → помечается (hamming ≤4)
- `near_duplicate_pair` → evidence downgrade

**Что улучшить:** Near-duplicate пары не исключаются полностью, только помечаются.

### Фактор 7: Calibration — **82/100** ✅
**Что требует ТЗ:** *«7 людей × 9 bins; LOPO; contamination hardening»*

**Что в коде:**
- `CalibrationModel`: person-balanced reference, per-bin per-zone
- `leave_one_dataset_sensitivity()`: LOPO на уровне датасетов
- `calibration_limited` flag при <3 matched sets

**Что улучшить:**
- P2-9: `consistency_check` не вызывается
- P1-5: CI при <2 кластерах
- P2-4: Cluster bootstrap для mean, не median

### Фактор 8: FDR control — **65/100** ⚠️
**Что требует ТЗ:** *«Канонический FDR 0.05; p95_point_z — порядковая статистика»*

**Что в коде:**
- `multiple_testing.py`: pair-level FDR + zone-level FDR
- `fdr05` и `fdr10` thresholds

**Проблемы (подтверждены аудитом):**
- P0-5: 81% пар <20 точек → single-z fallback (антиконсервативен)
- P1-6: `scale = m/n_eff` при `n_eff < m` — inflation (DIAGNOSTIC ONLY)
- P1-7: Zone FDR `n_eff` = все зоны всех пар (не по bin)
- P1-20: `fdr10` naming при пороге 0.05

### Фактор 9: Negative control — **80/100** ✅
**Что требует ТЗ:** *«На однородных данных — 0.45–0.55»*

**Что в коде:**
- `PointNoiseModel`, `DescriptorNoiseModel`, `MeshNoiseModel` — из калибровки
- `calibrated_score()` сравнивает с null distribution

**Проблемы:**
- P0-3: chronology baseline из основного датасета (self-calibration)
- P2-11: «Persistent» = всего 2 смежных кандидата (слабо)

### Фактор 10: Reproducibility — **93/100** ✅
**Что требует ТЗ:** *«Четыре контрольные суммы: data, code, model, config»*

**Что в коде:**
- `data_hash` (digest of all input files)
- `code_hash` (digest of all .py files)
- `model_hash` (digest of weights)
- `config_hash` (digest of Stage1Config/Stage2Config)
- Atomic directory commits
- Checkpoint/resume

**Сильнейшая сторона проекта.**

### Фактор 11: Хронологический отчёт — **25/100** ❌
**Что требует ТЗ (секция 5 из брифа редакции):**
- Уровень 0: Базовая линия (самые ранние фото)
- Уровень 1: Эпоха (1–2 года)
- Уровень 2: Фото внутри эпохи
- Уровень 3: Пара/переход

**Что в коде:**
- Stage 3 строит timelines по pose_bin (график p95_point_z)
- Narrative — 6 фиксированных параграфов
- Таблица всех пар с фильтрами

**Что НЕ реализовано:**

- Нет базовой линии как точки отсчёта
- Нет хронологического прохода от раннего к позднему
- Narrative не описывает конкретные изменения: *«в 2007 скуловая точка сместилась»*. Вместо этого: *«найдено N пар с аномальным темпом»*
- Нет карточки фото, нет карточки пары в журналистском формате

### Фактор 12: Сквозные наблюдения — **8/100** ❌
**Что требует ТЗ:** *«Наблюдение живёт от эпохи к эпохе: где родилось, повторилось, опровергнуто»*

**Что в коде:**
- `_persistence()` в engine.py: считает 2 смежных кандидата → `persistent_geometric_change`
- `corroboration.py`: cross-bin support count

**Что НЕ реализовано:**
- Нет сущности `Observation` с ID и историей
- Нет привязки наблюдения к зоне лица
- Нет статуса: слабый сигнал → усиление → устойчивый маркер
- Нет поля «что закроет вопрос»
- Нет связки: наблюдение из 2004 → подтверждение в 2007 → опровержение в 2010

**Это центральнаяmissing-фича проекта.**

### Фактор 13: Уровни уверенности — **30/100** ⚠️
**Что требует ТЗ:** *«low / medium / high — от сочетания признаков»*

**Что в коде:**
- Evidence states: `within_noise`, `coherent_jump_candidate`, `persistent_geometric_change`, `rate_change_candidate`, etc.
- Это **статусы измерения**, не уровни уверенности

**Что НЕ реализовано:**
- Нет агрегации: cross-bin + cross-era + persistence → high
- Нет шкалы для журналиста: `low/medium/high`
- `persistent_geometric_change` ≠ `high confidence` — может быть persistent в одном ракурсе
- Нет правила: *«сигнал в 2+ ракурсах + 2+ эпохах + persistence = high»*

## Главный вывод

**Предыдущий подрядчик довёл методологию до высокого уровня (80/100), но не построил продукт для журналиста (21/100).**

Сильные стороны — математика и инфраструктура:
- Pose isolation, calibration, FDR, hash quartet — работают
- Метод верифицирован экспериментами (AUC 0.9916)
- Код хорошо структурирован и задокументирован

Слабые стороны — всё, что видит журналист:
- Отчёт = приборная панель инженера, а не расследование
- Нет хронологического повествования
- Нет наблюдений как сквозной сущности
- Нет уровней уверенности
- Нет тезисных шаблонов

**Диагноз:** проект застрял на границе между *«научный инструмент»* и *«журналистский продукт»*. Мост между ними — генератор хронологического каркаса — не построен.
