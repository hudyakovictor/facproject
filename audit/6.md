**Дата аудита:** 2026-08-27
**Объект:** репозиторий `github.com/hudyakovictor/facproject`, ветка по состоянию на дату аудита
**Метод:** статический аудит кода (Stage 1–3, калибровка, FDR, хронология, evidence, отчёт), сверка с документацией проекта (`docs/final/*`, `validation/*`, `docs/CODE_AUDIT_50_ANALYSES.md`, `docs/DATA_COVERAGE_AUDIT.md`) и с ТЗ

## 0. Executive summary (для не-технических стейкхолдеров)

**Что делает система.** DEEPUTIN сравнивает фотографии одного человека за 1999–2026 гг. (1909 уникальных фото, 5561 пара) через 3D-реконструкцию лица (3DDFA_V3): выравнивает пары, измеряет расхождение 134 ключевых точек и плотной сетки, сравнивает текстуру, помечает пары, где изменение «слишком быстрое» или «слишком согласованное» относительно калибровочного шума.

**Главный вывод.** Архитектура продумана на удивление аккуратно: fail-closed принципы (NaN ≠ 0, отсутствие данных ≠ измерение, разные ракурсы не смешиваются), person-balanced калибровка, LOPO-чувствительность, evidence-слой с альтернативными объяснениями, осторожный язык отчёта (статусы — «кандидаты», не «вердикты»). Это **качественный скрининговый инструмент** для приоритизации пар под ручную экспертную проверку.

**Но как доказательство — использовать нельзя.** Четыре причины, по которым результаты в текущем виде не могут быть предъявлены в суде или журналистском расследовании как надёжные доказательства:

1. **Нет валидации на реальном ground truth.** Все заявленные метрики качества (AUC ≈ 0.99) получены на синтетических симуляциях и калибровочных парах одного-семи человек. Ни разу пайплайн не проверен на независимом наборе «точно разные люди» и «точно один человек» на реальных архивных фото разных эпох.
2. **Калибровка мала и нерепрезентативна.** 7 персон (а по ТЗ — вообще одно лицо; в материалах проекта противоречие). Нулевая модель «шума одного человека» построена на лицах, не похожих по демографии на целевую персону, и не учитывает старение.
3. **Статистическая коррекция не строгая.** Для 81% пар (менее 20 калиброванных точек) p-value считается по упрощённой формуле, которая **занижает значимость шума** (анти-консервативна), а затем умножается на эвристический «фактор зависимости» 5.83. Итоговый уровень ложных срабатываний не контролируется строго — он может быть как выше, так и ниже заявленных 5%.
4. **Систематические ошибки не устранены, а только помечены.** Расхождение ключевых точек коррелирует с разницей ракурсов (pose leakage, ρ ≈ 0.46): часть «аномалий» — это просто разные углы съёмки. Текстура сравнивается без нормализации освещения и позы и коррелирует с годом съёмки (r = 0.52). Эти эффекты помечаются флагами, но не вычитаются из решений.

**Что можно делать уже сейчас:** использовать DEEPUTIN как **фильтр-приоритизатор** — «вот пары, которые стоит проверить человеку», при условии что каждый кандидат проходит ручную проверку по протоколу `docs/final/14_FORENSIC_REVIEW_PROTOCOL.md`. Внутренний аналитический инструмент — да. Публичное доказательство — нет.

**Что нужно, чтобы можно было (минимум):** независимый тест-сет с известной истиной → расширенная калибровка (≥30 персон, разные возрасты/демографии) → строгий FDR (permutation-null вместо эвристики) → устранение pose leakage из первичных метрик → калибровка хронологических порогов на независимых данных → двойное слепое экспертное ревью. Детали — в §7–8.

## 2. Stage 1 — Извлечение признаков

### 2.1 3DDFA_V3 reconstruction
**Вердикт: методы корректны, есть известные систематические ограничения.**

- Один вызов сети на фото, атомарное сохранение всех представлений (object / normalized / canonical / chronology-aligned / camera / image-224), валидатор и hash-aware resume — правильная инженерия (`app6/stage1/engine.py`, `reconstruction.py`).
- QA-гейты на реконструкцию: reprojection p95 ≤ 5 px, outlier-детекция (>100 выпавших вершин → RuntimeError), upside-down sanity, detection confidence (`reconstruction.py` docstring). Это снижает риск «тихих» плохих реконструкций.
- **Bias по углу/освещению/экспрессии:** не измерен на реальных данных (нет test-retest одного фото через сеть). Из реестра результатов (`docs/final/09_RESULTS_REGISTER.md`): pose объясняет 46.1% вариации residual — т.е. реконструкция систематически зависит от ракурса. Это ожидаемо для 3DDFA, но означает, что **сырые метрики нельзя читать без контроля позы** (см. §3.7).
- **Границы бинов (известный, задокументированный дефект):** `geometry.classify_pose` — жёсткие границы; фото при yaw −9.9° (frontal) и −10.1° (left_light) получают разную каноническую коррекцию (0° vs −17.5°) — скачок 7.4° для соседних фото. Soft assignment (`nearest_canonical_yaw`) написан, но **не интегрирован** в пайплайн (docstring: «IN PROGRESS»). Для первичного канала это смягчено тем, что primary-сравнение идёт в raw-координатах с попарным Kabsch, а не в chronology-координатах; но для chronology-канала и для гейта позы эффект остаётся.

### 2.2 Pose estimation (pitch/yaw/roll)
**Вердикт: приемлемо для гейтинга, но ошибка углов не валидирована.**

- Углы берутся из 3DDFA_V3 (один вызов). Точность на архивных фото (разное качество, VHS-оцифровка) не измерена — нет ground truth по углам.
- Ошибка углов наследуется гейтом `pose_gap`: пара с истинным разбросом 11° может быть пропущена (оценка 11.9°) или отброшена (оценка 12.1°) при пороге 12°. Для профильных бинов с порогом 2° ошибка углов критична.
- **Рекомендация:** добавить test-retest по углам (одно фото через сеть N раз / разные детекторы) и валидировать на синтетических поворотах.

### 2.3 Landmark extraction (106/134)
**Вердикт: стабильность не измерена напрямую; косвенно — приемлемо.**

- Ландмарки — индексы вершин BFM (не регрессия координат), что даёт согласованность схемы 106/134.
- Per-landmark confidence = visibility × reprojection factor × front-facing (`engine.py`).
- **Нет test-retest стабильности** (повторная реконструкция того же фото). Робастность проверена только на синтетическом шуме: σ 0.002→0.010 даёт AUC 0.9935→0.9886 (raw) — падение малое, но это симуляция, не реальная реконструкция.
- Порядок ошибки: из калибровки медианный same-person RMSE ≈ 0.0046–0.0122 (в нормализованных единицах). Это «реконструкционный шум», но фактически он включает фотографическую вариативность (свет, камера, мимика) — для нулевой модели это даже правильнее, но название «reconstruction noise» неточно.

### 2.4 Texture extraction
**Вердикт: извлекается корректно, но используется не для сравнения.**

- Stage 1 извлекает UV-текстуру, альбедо (`alpha_alb`) и затенение (`alpha_sh`) — то есть **разделение освещения и альбедо уже есть в пайплайне**.
- Однако Stage 2 сравнивает текстуру **в image-space (2D-патчи исходного фото)**, а не UV/альбедо: LBP, GLCM, Gabor, Laplacian, градиенты по зонам качества (`texture_image.py`). Явное предупреждение в коде: **«No pose normalization applied yet»** (`texture_image.py:338,345`).
- **Вывод:** разное освещение и ракурс напрямую меняют текстурные дельты; альбедо-канал, который мог бы это скомпенсировать, не используется для сравнения. Частичная митигация: quality gate (разрешение, нейтральный скор) и политика «texture = visualization only, никогда identity evidence» (`metric_registry.py`, `evidence.py`). Это корректное решение — но означает, что **текстурные дельты в отчёте/UI нельзя интерпретировать как признак материала/силикона** (см. §3.9).

### 2.5 Alpha coefficients (identity/expression)
**Вердикт: извлекаются корректно; интерпретация — с оговорками.**

- `alpha_id` (identity, 199 коэфф.) и `alpha_exp` (expression) сохраняются; `alpha_id_l2` калибруется по same-person null внутри pose bin.
- **Коллинеарность:** alpha_id коррелирует с позой (pose объясняет 46.1% вариации). Per-bin калибровка частично это учитывает, но внутри bin остаётся остаточная поза-зависимость.
- **Слабость канала:** по реестру результатов alpha_id как единственный канал имеет ci_lo 0.6768 — слабый дискриминатор. При этом `alpha_id_jump_candidate` **может повысить статус пары до reportable** (`alpha_chronology.py`, `evidence.py: REPORTABLE_CHANGE_STATES` содержит `alpha_id_change_candidate`). Это риск: отчётный кандидат может опираться на слабый канал. (P1, см. §7.)

## 3. Stage 2 — Сравнение пар

### 3.1 Pose binning
**Вердикт: 9 бинов фиксированы, пороги позы калиброваны по AUC; но покрытие неравномерно, и гейт для frontal почти инертен.**

- Бин-центры yaw: 0, ±17.5, ±32.5, ±45, ±70; frontal = [−10°, +10°) — ширина 20°.
- Пороги yaw-gap из `atlas/pose_gate_v2.csv` **выведены из данных** (колонка `auc_at_limit`): frontal 12°, light 6–8°, mid 4°, deep 2°, left_profile 2° (внутри 10° подбинов), **right_profile 0° → все пары right_profile отклоняются** (`bin_below_snr3`). Это честно, но означает выпадение правого профиля (~20% калибровочного материала: 188/943 кадров) из primary-сравнения; left_profile с порогом 2° тоже почти не даёт измеримых пар.
- **Frontal:** бин шириной 20° при пороге 12° — пары с разбросом 12–20° отбрасываются, но пары с разбросом до 12° проходят, и для них остаётся заметная остаточная поза. Из документации: ослабленные пороги пропускают 93.1% пар — «гейт фактически инертен» (`analysis_policy.py` docstring). Т.е. **разбиение на бины не обеспечивает строгой сопоставимости внутри frontal** — это компенсируется только попарным Kabsch и флагом pose leakage.
- **Профили:** median common points 19 (bin-level) при пороге 30 для ldm134; попарно медиана 63 — профили проходят попарный гейт, но калибровочное покрытие per-landmark в профилях бедное (см. §3.10).

### 3.2 Kabsch alignment
**Вердикт: методологически корректный robust alignment.**

- Iteratively-trimmed Kabsch (trim 15%, до 5 итераций), **без масштаба** (важно: не поглощает разницу размера лица), на якорном подмножестве (per-bin якоря из `landmark_utility.npy` / центрально-квантильный fallback), residual считается по всем общим точкам (`core.py`).
- Локальные изменения (мимика/кость) не поглощаются глобальным преобразованием — они остаются в residual. Это ровно то, что нужно для задачи.
- Alignment quality измеряется, но **не гейтит** пары (D-003: Spearman +0.096 с residual — некоррелирован). Разумное решение; порог 0.5 — справочный.
- **Артефакты alignment:** при малом числе общих точек (<8) fallback на обычный Kabsch без trim; при <min_points — «kabsch_insufficient_for_trimming». Риск мал, но для пар с 8–30 точками trim-устойчивость снижается (см. §3.10).

### 3.3 Residual pose leakage
**Вердикт: измеряется и помечается, но не устраняется. P1.**

- `pose_leakage_diagnostic` считает Spearman ρ между `pose_distance` и метриками; порог флага 0.45. По замеру проекта ρ(pose_distance, ldm134_rmse) = 0.463 → **ldm134_rmse помечается как pose_leakage_candidate**.
- Митигация: пары с `pose_distance > 1.0` получают `pose_leakage_limited` (evidence_state понижается). Пары с pose_distance ≤ 1.0 — **не помечаются**, хотя зависимость непрерывна, а не пороговая.
- Модуль `subtract_angle_noise` (который мог бы вычитать угловой шум) **не влияет на скоринг** (см. §3.6).
- **Вывод:** primary-метрики (ldm134_rmse, p95_point_z) частично пересчитывают ракурс; текущие пороги недостаточны для полного контроля. Требуется либо стратификация null по pose-gap, либо коррекция по измеренной sensitivity (не единой константой — это в проекте уже запрещено, и правильно).

### 3.4 Dense mesh comparison
**Вердикт: валиден как support-канал; в основном некалиброван.**

- 35709 вершин (или фактическое число из npz), identity-only mesh (если есть) → сравнение в normalized-пространстве; иначе object_normalized. Якоря до 6000 вершин, trim-15% Kabsch, residual + point-to-plane по нормалям A (`mesh_dense.py`).
- **Риск смешения пространств:** если у одной записи есть `vertices_identity_only`, а у другой нет, сравниваются normalized (RMS-масштаб) и object_normalized координаты — пространства разные, а row только записывает `mesh_space_a/b` **без fail-closed** (P2).
- **Калибровка:** `MeshNoiseModel` требует mesh в калибровочном наборе; по коду «calibration datasets often lack full Stage-1 reconstruction meshes» → статус `unavailable`, mesh остаётся `direct_uncalibrated_dense_residual`. Т.е. для большинства пар mesh-метрики — **некалиброванный support**, и это честно отражено в `mesh_evidence_level`.
- Зоны (анатомические, `mesh_zone_indices.json`) скорингятся через zone FDR — но z-скор относительно некалиброванного/бедного null.

### 3.5 Texture descriptors
**Вердикт: корректно исключены из evidence; как измерение — невалидны для выводов.**

- Сравнение 2D image-space патчей по зонам, без нормализации позы и освещения (см. §2.4). Quality gate блокирует текстурные выводы при quality_limited или разрешении >2× (`quality_gate.py`, `pair_row_patch.py`).
- В реестре метрик текстура помечена `evidence_role: visualization_only` и исключена из evidence-канала (`metric_registry.py`). **Это правильное и важное решение.**
- **Era bias (r = 0.52 с годом):** частично адресуется quality gate (нейтральный скор 0.5 при ограниченном качестве), но явной стратификации текстуры по эпохе/источнику нет. Для отчёта достаточно, для любых текстурных «выводов» — нет.

### 3.6 Angle noise subtraction
**Вердикт: вычисляется, но НЕ применяется к решениям. P1 — расхождение заявленного и фактического.**

- `subtract_angle_noise` подбирает калибровочную пару того же человека с близкой разницей углов (±2° yaw, ±1° pitch/roll) и вычитает её метрику из наблюдаемой (`angle_noise.py`).
- **Но в `engine.py` scores строятся из `c.metrics` (raw), а компенсированные поля (`*_angle_compensated`) только записываются в строку** и нигде дальше не потребляются (проверено grep: только API-эндпоинт `noise_calibration` их читает). Т.е. **угловой шум фактически не вычитается ни из одного решения** (статусов, z-скоров, FDR).
- Дополнительно: оценка шума — по **одной** калибровочной паре (высокая дисперсия), при отсутствии совпадения — `angle_noise_uncompensated` (честно, но часто).
- **Рекомендация:** либо подключить компенсацию в скоринг (с оговорками), либо убрать из отчёта утверждения о компенсации. Сейчас это «декоративный» модуль.

### 3.7 Calibration model
**Вердикт: методика грамотная (person-balanced, LOPO, cluster bootstrap, reuse-cap), но выборка мала и есть противоречие в её составе. P0/P1.**

- 943 кадра, 7 датасетов, 9 бинов. Референсы — person-balanced (медиана персональных квантилей), CI — cluster bootstrap (кластеры = датасеты), LOPO-чувствительность, reuse-cap 3 с штрафом для matched-null (`calibration.py`, `robustness.py`).
- **Противоречие состава:** `docs/final/05_CALIBRATION_PROTOCOL.md` заявляет «семь разных людей», а ТЗ (`aboutplatform.txt`) — «на калибровочных фото везде моё лицо… заранее известно, что это один и тот же человек». Если калибровка — **одно лицо в 7 сессиях**, то нулевая модель «шума одного человека» построена на геометрии одного человека и **не переносится** на целевую персону (другая геометрия черепа, возраст, качество реконструкции). Это P0 для любых абсолютных порогов. Противоречие должно быть разрешено владельцем, и состав набора зафиксирован в манифесте.
- Даже при 7 персонах: LOPO spread > 0.35 помечает референсы как unstable/sparse → пары получают `calibration_limited` (механизм честный). Профильные бины (median 19 общих точек) — заведомо бедная калибровка.
- **Matched-null чувствителен к худшей паре:** порог `calibrated_score` = max(reference p95, matched p95), где matched p95 из ≤7 значений ≈ максимум. Один выброс/хаб определяет порог; reuse-cap смягчает, но не устраняет.
- **Дефект кода (P2):** в `CalibrationModel._build_references` переменная `ci` присваивается только при ≥2 конечных кластерах, но читается безусловно — при <2 конечных кластеров переиспользуется CI предыдущей метрики (stale value). Влияет на публикуемые `ci_lo/ci_hi` некоторых референсов.

### 3.8 Point support / calibrated_point_count
**Вердикт: 81% пар с <20 точками — это ограничение достоверности, а не только уверенности. P1.**

- `calibrated_point_count` — число точек с per-landmark null (ref.count ≥ 7). Для профильных бинов и части frontal-пар покрытие бедное → <20 точек у 81% пар.
- Последствия: (а) `p95_point_z` считается по <20 точкам — сама метрика шумная; (б) в FDR для m<20 используется **single-z fallback** (см. §3.11) — анти-консервативный; (в) статусы для таких пар должны трактоваться как diagnostic/limited. В коде это частично есть (`mt_point_support = limited`, `mt_role_detail`), но **порог значимости и статусы не понижаются автоматически** — пара с m=10 может получить `coherent_jump_candidate` наравне с m=80.
- **Вывод:** это не «invalidates», но существенно снижает уверенность; требуется явная градация статусов по m (например, m<20 → только «scattered/uncertain» или требование corroboration).

### 3.9 FDR correction (BH)
**Вердикт: реализация BH корректна, но применение к данным — с двумя серьёзными оговорками. P1.**

- `benjamini_hochberg` — стандартная step-up процедура с монотонными q (`fdr_control.py`). Корректно.
- **Оговорка 1 (анти-консервативный fallback):** для m<20 точек p95_point_z трактуется как одиночный N(0,1) z: `p = erfc(|z|/√2)` (`multiple_testing.py:_p_from_z`). Под нулевой гипотезой p95 из m точек ≈ 1.28–1.65, поэтому p95=2.5 даёт p≈0.012 вместо правильного (порядковая статистика) p≈0.3–0.6. Для 81% пар p-значения **занижены** → завышенная значимость. Правильная порядковая статистика (`_p_from_p95_z`) применяется только при m≥20.
- **Оговорка 2 (эвристическая инфляция):** q-значения умножаются на `m/n_eff`, где n_eff = photo_count//2 = 954 → множитель 5.83. Это **не валидная FDR-процедура** для зависимых данных: BH гарантирует контроль FDR при независимости/положительной зависимости; масштабирование q на константу эквивалентно тесту на уровне 0.05/5.83 ≈ 0.0086 (при независимости) — но реальный уровень при зависимых данных неизвестен и может быть как выше, так и ниже. Фактор 5.83 — эмпирический, не теоретический.
- **Сетевое следствие:** заявленный «FDR ≤ 0.05» не является строго контролируемым уровнем. Рекомендация: permutation-null на уровне пар (перестановка дат/фото) или cluster-based коррекция; убрать множитель как «поправку».

### 3.10 Multiple testing
**Вердикт: FDR покрывает только один канал (p95_point_z). P1.**

- 5561 пар → 5561 тестов по primary-каналу — поправка есть (с оговорками §3.9).
- **13 descriptor families** (по 134 ландмарка × 13 признаков), **6 mesh-метрик**, texture — **не входят в FDR**. Статусы `descriptor_jump_candidate` / `mesh_elevated` используют эвристические пороги (z ≥ 3, p95_z ≥ 3.5, доля значимых ≥ 0.15) без контроля множественности. Zone FDR покрывает только zone-метрики.
- При 5561 парах × 13 семейств ≈ 72 тыс. неявных тестов — без коррекции часть «кандидатов» — артефакт множественности.
- **Рекомендация:** включить descriptor/mesh в общую коррекцию или явно пометить их статусы как «нескорректированные по множественности».

### 3.11 Chronology rate flags
**Вердикт: пороги хардкод; референс темпа строится на самом основном датасете (self-referential null). P1.**

- Пороги: same_day — pz ≥ 4.5, coh ≥ 0.35; fast — 0<d≤60, pz ≥ 4.5, sig ≥ 0.15, coh ≥ 0.45, rate_z ≥ 3.0; medium — 60<d≤180, pz ≥ 5.5, sig ≥ 0.18, coh ≥ 0.5, rate_z ≥ 3.5 (`chronology.py`). **Хардкод, не калиброваны на calibration set** (в отличие от pose_gate).
- `rate_z` считается относительно **эмпирического распределения rate внутри того же pose bin основного датасета** (`_robust(rates)` из adjacent-пар самого прогона). Это противоречит заявленному принципу «порог обучается только на calibration split» (`docs/final/06_STATISTICS_AND_THRESHOLDS.md`) и создаёт самомаскировку: если аномалия массовая (например, эпоха смены источников), референс раздувается и индивидуальные аномалии не видны; если аномалия единичная — референс почти не зависит от неё, но включает её в «норму».
- Хронологические статусы **перезаписывают** `row['status']` (например, `persistent_rapid_change_candidate`) — финальный статус есть фьюжн геометрии+motion+descriptor+chronology, что усложняет интерпретацию (см. §6).

### 3.12 Baseline return / irreversible return
**Вердикт: «baseline return» на деле — детекция реверса, а не возврата к базе; истинный A→B→A-детектор не подключён. P2.**

- `apply_baseline_return` проверяет, что следующее ребро B→C противоположно A→B (opposite_fraction ≥ 0.45, median_cosine ≤ −0.20, magnitude_ratio 0.35–2.75). Это **реверс движения**, а не «возврат к состоянию A» — C не сравнивается с A. Название вводит в заблуждение; пороги эвристические.
- `detect_irreversible_return` (настоящий A→B→A через ≥5 лет, similarity ≥ 0.95, divergence ≥ 2×) — **не вызывается в production-движке** (проверено grep: только тесты и API-чтение файлов). При этом `SIMILARITY_CALIBRATED = False` — порог 0.95 не калиброван.
- **Вывод:** заявленная в ТЗ детекция «возврата к базовой линии» в проде реализована как слабый суррогат (реверс), а строгий детектор существует, но не работает.

### 3.13 Expression gate
**Вердикт: выключен (осознанно), влияние мимики только диагностическое. P2.**

- `expression_pair_gate.py` всегда возвращает `accepted: True`; рассогласование smile/jaw записывается в диагностику.
- Влияние мимики на первичную геометрию частично компенсируется identity-only каналом (`identity_only_ldm134_rmse`, `identity_only_motion_rmse`) и диагностическим `expression_influence = 1 − identity_rmse/full_rmse` (порог альтернативного объяснения 0.45).
- **Стратификации null по мимике нет** (есть только по качеству, и та не активирована по умолчанию — см. §3.14). Пары «улыбка vs спокойно» анализируются наравне; для ландмарков рта/челюсти это прямой конфаундер. Рекомендация: для пар с jaw/smile mismatch понижать evidence-уровень (не только добавлять reason).

### 3.14 Quality gate
**Вердикт: частично активен; стратификация по качеству не применяется по умолчанию. P2.**

- Активно: `quality_limited` (qmin < 0.35 / quality_status weak / zone-limited), `compensate_quality_disparity` (разрешение >2× → texture_conclusions_allowed=False, нейтральный texture-скор 0.5) — подключено через `enrich_pair_row` (`pair_row_patch.py`).
- **Не активно:** стратифицированные null-референсы (`pose_bin::q_stratum`) существуют только если калибровка пересобрана со стратами; `has_stratified_references()` в обычном прогоне False → `stratum=None` → общий пул. `threshold_multiplier` (1.0/1.45/2.05) записывается в строку, но **не применяется** к порогам.
- **Era bias:** гейт ловит разрешение и «quality_limited», но не ловит JPEG-артефакты/плёночное зерно/освещение как таковые. Для геометрии это менее критично, для текстуры — критично (но текстура и так visualization-only).

## 4. Stage 2b — Пост-обработка и corroboration

### 4.1 Cross-bin corroboration
**Вердикт: методологически корректно, с честными ограничениями.**

- Подтверждение ищется только среди adjacent-пар других pose bins в окне ±45 дней; требуется пересечение интервалов изменения и чтобы поддерживающая пара сама была кандидатом (`corroboration.py`). Учитываются независимые source groups.
- Ограничение: corroboration не проверяет «то же направление/тип изменения» — только совпадение дат, статус-кандидат и пересечение top-5 descriptor families (слабый сигнал). Статус `corroborated_multiple_pose_bins` поэтому не следует читать как «подтверждённое изменение» — это «согласованный кандидат».
- Корректно: cross-bin никогда не меняет primary-метрики (policy в коде).

### 4.2 Lead registry
**Вердикт: data leakage не обнаружен.**

- Лиды из имён папок архива (`top_identity_breaks.json` и т.п.) используются только как приоритет и покрытие; явная политика «never ground truth or threshold tuning» (`leads.py`, `stage2b/engine.py` AA01: overlap с prior — не независимое подтверждение). Пороги от лидов не зависят. OK.

### 4.3 Evidence packets
**Вердикт: продуманы; есть риск переоценки статусов (P2).**

- Пакет содержит measurements, calibration, quality, alternative_explanations, source_files — хорошая структура.
- **Риск переоценки:** `alpha_id_change_candidate` и `coherent_jump_candidate` (одноразовый скачок) входят в `REPORTABLE_CHANGE_STATES` наравне с `persistent_geometric_change`. Одноразовый скачок — слабое evidence; в отчёте это различается текстом, но статусы в таблицах UI выглядят одинаково «сильно».

## 5. Stage 3 — Интерпретация и отчёт

### 5.1 Narrative generation
**Вердикт: корректно, без сенсационности.**

- Нарратив фиксированный, фактологический: «Ни один статус сам по себе не доказывает подмену личности, маску, операцию или причину изменения»; отдельно сообщается о неполном калибровочном покрытии (`poor` соседних сравнений) и о том, что старые лиды — только цели перепроверки (`stage3/engine.py`). Соответствует данным.
- Замечание: число «кандидатов» (348 change points) в UI подаётся крупно; без контекста «это кандидаты на ручную проверку, а не находки» читатель может переоценить. Рекомендуется выносить disclaimer в шапку, а не только в narrative/footer.

### 5.2 Motion maps
**Вердикт: визуализация достоверна (данные реальные), интерпретация — с оговоркой.**

- Карты движения строятся из фактических векторов/значимости (`ldm134_point_z`, `significant`) по top-40 пар по p95_point_z. Красные точки = «выше калибровочного шума» — это честно.
- Оговорка: «выше шума» ≠ «изменение лица» — это превышение same-person null, который сам содержит позу/свет/мимику (см. §3.7). В легенде это не разъяснено.

### 5.3 Status → evidence_state mapping
**Вердикт: mapping в целом корректен, неопределённость сохраняется.**

- `STATUS_TO_EVIDENCE_STATE` — 1:1 с понижениями: quality_limited / calibration_limited / pose_leakage_limited приоритетнее статуса (кроме within_noise) (`evidence.py`). Неизвестные статусы → `elevated_uncertain` (fail-safe).
- Замечание: legacy-имена `mt_significant_fdr10` / `mt_fdr10_diagnostic_flag` при фактическом пороге 0.05 — вводят в заблуждение при чтении данных (P2).

### 5.4 Public safety report
**Вердикт: соответствует заявленным ограничениям.**

- Lint запрещённых терминов («двойник», «подмена», «силикон», «маска»…) по evidence-пакетам (`postprocess_reports.py`), `public_safety_status` в манифесте; Stage 3 не публикует пары, не прошедшие evidence-gate (`is_reportable_change` + RuntimeError при нарушении). Хорошо.

## 8. Ответы на конкретные риски ТЗ (§4)

### 4.1 Систематические ошибки
- **Pose leakage:** да, присутствует (ρ = 0.463 для ldm134_rmse). Текущие пороги недостаточны: помечаются только пары с pose_distance > 1.0, метрики не корректируются, угловая компенсация не влияет на скоринг (R2, R6).
- **Texture = era bias:** r = 0.52 учтён частично (quality gate, visualization-only). Явной стратификации по эпохе нет (R9).
- **Calibration coverage:** ~46 кадров left_profile вне диапазона — да; профильные бины — бедная калибровка и узкие гейты (R5). Покрытие должно публиковаться per-bin в отчёте (сейчас есть в `calibration_sensitivity.json`).
- **Point support bias:** 81% пар <20 точек — не invalidates, но понижает до Diagnostic; FDR для них анти-консервативен (R1).

### 4.2 Статистические риски
- **FDR на зависимых данных:** порядковая статистика для p95 — корректное приближение при независимости точек; независимость нарушена (пространственная корреляция ландмарок), признано в коде. Требуется эмпирический null.
- **Dependence inflation x5.83:** эмпирическая эвристика (m/n_eff), не теоретическая; не валидная FDR-процедура (R13).
- **Threshold calibration:** pose_gap — data-driven (AUC at limit, `pose_gate_v2.csv`); chronology rate — хардкод; same-day — хардкод в проде; baseline return — эвристика; irreversible return — не калиброван.
- **Multiple comparisons:** 5561 пар × 13 семейств × mesh/texture — коррекция только на p95_point_z (R7).

### 4.3 Интерпретационные риски
- **Status ≠ verdict:** корректно донесено в narrative и evidence-политике; UI показывает статусы без per-row caveat (R22).
- **Confounders:** освещение/разрешение/JPEG частично учтены (quality gate, alternative_reasons); JPEG-артефакты и возраст камеры явно не моделируются.
- **Temporal confounding:** естественное старение не моделируется; «базовая линия» — это same-person null из калибровки (молодые лица), не возрастная модель. Изменения 1999→2026 могут быть старением; rapid-change флаги — единственная (слабая) защита.

## 9. Ключевой вопрос: суд / журналистское расследование

**Можно ли предъявить текущие результаты как надёжные доказательства? — Нет.**

**Почему (по убыванию критичности):**
1. **Нет валидации на реальном ground truth.** AUC ≈ 0.99 получены на симуляциях и калибровке; на реальных архивных фото разных эпох/качеств пайплайн не проверен. Без независимого тест-сета «известно разные люди / известно один человек» любые AUC — заявления, а не измерения.
2. **Калибровка нерепрезентативна** (7 персон или 1 персона; один демографический профиль; нет возрастного диапазона целевой персоны). Null «шума одного человека» может не соответствовать целевой персоне.
3. **Статистическая коррекция не строгая** (R1, R13): уровень ложных срабатываний не контролируется на заявленном 0.05.
4. **Pose leakage не устранён** (R6): часть «аномалий» — артефакт ракурса.
5. **Хронологические флаги не калиброваны** (R8), **текстура невалидна как evidence** (R9), **alpha-канал слаб** (R10).
6. **Конфликт интересов/воспроизводимость:** калибровка — лицо владельца (по ТЗ); единственный оператор; веса и данные не в репозитории; воспроизводимость прогона не проверена сторонним лицом.

**Что конкретно исправить, чтобы можно было (приоритетный порядок):**
1. Независимый тест-сет с известной истиной (same-person и different-person пары, архивные фото разных эпох/качеств/источников) → измерить TPR/FPR/AUC на нём; опубликовать operating points.
2. Расширенная калибровка (≥30 персон, разные демографии и возрасты; зафиксировать состав в манифесте) → пересчитать все null.
3. Строгий FDR: permutation-null на уровне пар с кластеризацией; убрать эвристический множитель; исправить fallback для m<20.
4. Устранить pose leakage из первичных метрик (стратификация null по pose-gap или коррекция по измеренной sensitivity; жёстче гейты для frontal).
5. Калибровка хронологических порогов на независимых данных; публикация TPR/FPR по каждому флагу.
6. Валидация углов/ландмарок 3DDFA на реальных данных (test-retest, cross-camera).
7. Экспертный протокол: два независимых слепых ревьюера, пререгистрация гипотез, adjudication (протокол в `docs/final/14_FORENSIC_REVIEW_PROTOCOL.md` — хорошая основа, нужно внедрить).
8. Полная воспроизводимость: веса/данные/конфиги/хеши доступны рецензенту; сторонний прогон.

**С чем можно работать уже сейчас:** скрининг и приоритизация пар для ручной проверки; внутренняя диагностика; формулировки в отчёте — «наблюдение движения точек превышает калибровочный шум», не более. Это не «доказательство подмены/маски/операции».

## 13. Подтверждённые кодом находки второго прохода (воспроизводимые)

### 13.1 P1 — Краш Stage 2 при калибровке из опубликованного архива (sidecar/legacy)
**Файл:** `app6/stage2/calibration.py`, `_build_references`, строки 74–106.
**Механика:** в каждой ячейке `(pose, metric)` при `>1` калибровочном датасете: нет `<2` датасетов с конечными значениями (ветка `insufficient_clusters_after_filter`) → после неё безусловно выполняется `ref["ci_lo"] = ci["ci_lo"]` и т.д., где `ci` не определён → `NameError`. Внешняя ветка `len(set(ids)) < 2` безопасна.
**Триггер:** alpha-метрики (`alpha_id_l2`, `alpha_exp_l2`) при калибровке, загруженной через `load_calibration_from_sidecar` или `load_legacy_calibration_archive` — оба режима заполняют `alpha=NaN` (`_missing_alpha`) → все значения ячейки NaN → `finite_ids = []` → внутри-ветка else → `NameError` при построении `CalibrationModel`. Оба режима — официально поддерживаемые входы `load_calibration` (опубликованный архив `person_*/frame_*/metadata.json` и legacy `info.json`). Полный Stage 1 (реальные alpha) краша не даёт — поэтому в прогонах «из свежих данных» дефект не проявлялся.
**Воспроизведение:** автономный скрипт, повторяющий точную логику строк 74–106, даёт `NameError: cannot access local variable 'ci'` для случая «2 датасета, все значения NaN».
**Фиксация:** инициализировать `ci = None` до ветки и записывать CI-поля только при `ci is not None`; добавить юнит-тест на all-NaN метрику.

### 13.2 P1 — same_day_gate и irreversible_return фактически не в продакшене
**Файлы:** `app6/stage2/engine.py` (импортный список), `same_day_gate.py`, `irreversible_return.py`.
**Факты:** ни один из модулей не импортируется и не вызывается в `Stage2Engine.run()`. В проде «same-day conflict» даёт хардкод-эвристика `chronology.py` (`pz ≥ 4.5 ∧ coh ≥ 0.35`), а не data-driven 12σ-гейт (R15). При этом `engine.py` в блок `_modules` включает запись `'same_day_gate_v2': {'imported': True, ...}` — **манифест утверждает импорт и применение модуля, которого нет в коде** (вводит в заблуждение при верификации прогона). `irreversible_return` вызывается только из тестов и `api/research_timeline.py` (чтение ключей артефактов), не из анализа пар.

### 13.3 P1 — Атласные артефакты отсутствуют; A11-якоря не действуют
**Факты:** в `app6/atlas/` физически есть только `pose_gate_v2.csv` и `pose_policy_v3_9bins.csv`. `run_manifest.build_manifest` жёстко ждёт `landmark_utility.npy`, `visibility_prior.npy`, `landmark_utility_manifest.json`, `texture_zones_bfm35709_v3.npz` → `manifest["ready"]=False`, `missing_artifacts` непусто — запущенный прогон **не соответствует** критерию готовности манифеста. ### 13.5 P2 — мелкие подтверждённые расхождения
- `skin_zone_atlas_final.py` — 477 строк мёртвого кода («NOT WIRED (AUDIT-05)»): атлас v4/40 зон никогда не подключался.

### 13.6 Положительные стороны, подтверждённые кодом
- Person-balanced reference: `median of per-person quantiles`, требование ≥3 персон, `count=0` при недостатке (не тихая подмена).
- Кластерный bootstrap CI (кластер = датасет) с явной оценкой недочёта ширины наивным bootstrap — честный отчёт о зависимости наблюдений.
- Ограничение повторного использования калибровочных кадров в matched-null (max 3, штраф 0.75) с hub-отчётом — защита от «хаба».
- LOPO-чувствительность p95 по датасетам (`calibration_sensitivity.py`) — пересчёт без повторного построения всех пар; «стабильно» при разбросе ≤35%.
- Fail-closed обращение с NaN: `calibrated_score` возвращает `not_measurable` для NaN (исправлено по аудиту N1/N2), не приводит к «elevated»-ложным срабатываниям.
- Порядок «измерение → применимость → evidence_state → reportable-фильтр»: `is_reportable_change` требует `adjacent` + `evidence_state` в whiteliste, `validation.py` (контракт) отклоняет утечку texture/uv-ключей в evidence-канал, date-contract сверяет даты (conflict → downgraded).
- `space_manifest`: запрет chronology-пространства и явное обоснование (D-003) с публикацией AUC-замеров (raw 0.9965 / aligned 0.9974 / chronology 0.9924) — прозрачно.
