## 📊 ПРОБЛЕМА

Обе метрики чувствительны к окклюзии при повороте головы:

| Метрика | Формула | Чувствительность |
|---------|---------|------------------|
| `mesh_visible_fraction` | `common_ids.size / MESH_COUNT` | Высокая |
| `mesh_common_vertex_count` | `common_ids.size` | Высокая |

**Причина:** При повороте головы (frontal → profile) окклюзия увеличивается:
- Frontal: видно ~95% вершин
- Profile: видно ~60% вершин
- Внутри pose bin разница может быть 10-15%

**Идея:**
```python

expected_visibility = {
    'frontal': 0.95,
    'left_light': 0.90,
    'left_mid': 0.85,
    'left_deep': 0.75,
    'left_profile': 0.60,
    # ... симметрично для right
}

# Нормализовать
mesh_visible_fraction_normalized = mesh_visible_fraction / expected_visibility[pose_bin]
```

**Проблемы:**
- ❌ Требует калибровки: много same-person пар для каждого pose bin
- ❌ Нестабильно: expected visibility зависит от качества Stage 1 reconstruction
- ❌ Сложно: нужно обновлять калибровку при изменении Stage 1
- ❌ Не решает проблему: нормализация не устраняет окклюзию

**Вывод:** Не рекомендуется.

## 📋 ОБҮРУНТОВАНИЕ

### Почему не исправляем:

1. **Нормализация нестабильна** — зависит от качества Stage 1
2. **Окклюзия неустранима** — это физическое ограничение, не ошибка кода
3. **Другие метрики устойчивы** — `mesh_rmse`, `mesh_p95` не зависят от окклюзии

### Почему не удаляем:

1. **Полезна для диагностики** — помогает понять почему mesh alignment не сработал
2. **QC флаг** — можно использовать для фильтрации плохих пар
3. **Обратная совместимость** — не ломаем существующий код

### Почему исключаем из хронологии:

1. **Чувствительна к углу** — не отражает реальные изменения
2. **Дублирует информацию** — `mesh_rmse` и `mesh_p95` более надёжны
3. **Может ввести в заблуждение** — журналист может неправильно интерпретировать
